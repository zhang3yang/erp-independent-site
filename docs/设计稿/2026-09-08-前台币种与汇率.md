# 前台币种切换与汇率换算 + 语言切换器改下拉 设计

日期：2026-09-08
涉及：`station-site`（Nuxt 前台）、`station-console-ui`（管理台）、`station-console`（后端）、`sdsstation`（库）

---

## 1. 要做的东西

前台顶栏两件事：

1. **语言切换器从一排链接改成下拉框**。现在 8 种语言平铺在顶栏，占满一行。
2. **新增币种切换器**。买家选一个币种，商品价格按汇率自动换算显示。

基准币种就是管理台里配的那个（`u_s_siteinfo.currency`）——商品价格本来就是用它存的。汇率每天从外部 API 自动拉取，运营可以手工覆盖。

一句话范围：**展示层换算。买家看到的是参考价，落进库的金额永远是站点本币。**

不做的（一期）：按 IP 猜币种、汇率历史曲线、每个商品单独定多币种价、把币种写进 URL 做多币种 SEO。

## 2. 四个已定的决定

### 2.1 汇率自动拉 + 允许手工覆盖

汇率源 `https://open.er-api.com/v6/latest/USD`：免费、不需要 API key、166 个币种、每天更新一次。**2026-09-08 在 49.234.194.194 上实测可达，818ms**（这台机器出网受限，GitHub 和一批镜像不通，所以这条必须实测过才能写进方案，见 memory `server-network-limits`）。同时测通的备选还有 `api.frankfurter.app`（ECB 数据）和 `api.exchangerate-api.com/v4`。

但**只有自动是不够的**，所以库里同时留一列手工覆盖：

- 免费 API 没有 SLA，哪天挂了不能让整站没价格；
- 外贸站常常故意把汇率打高一点留 buffer，这是业务决定，不该改代码。

生效规则：**手工覆盖压过自动拉取，逐币种生效**（覆盖了 EUR 不影响 CNY）。

### 2.2 币种不进 URL，走 Cookie

语言必须进 URL——Google 要能索引到每个语言版本，现在的 `hreflang` 就是靠这个。币种**不能**进 URL：每个页面会变成 8 种语言 × N 种币种的重复内容，SEO 上是灾难。

用 Cookie 而不是 `localStorage`：Nuxt 是 SSR，服务端渲染时要读得到当前币种。用 `localStorage` 的话服务端渲染出的是本币、客户端 hydrate 后才跳成欧元——首屏闪一下，而且会报 hydration mismatch。

### 2.3 结算页回到本币，订单落库也是本币

商品列表、详情、购物车都按买家选的币种显示。**到结算页明确切回本币**，并标注「≈ €184.00，最终以 USD 为准」；`u_s_order` / `u_s_orderitem` 一行不改。

理由：站上本来就不收款，`u_s_order` 的定义是「下单请求」，真正的报价和收款走线下和 ERP。既然如此，订单金额必须有一个**稳定的口径**——否则三个月后汇率变了，这张单到底是 €184 还是 $200 就成了糊涂账，而且运营在管理台看订单列表时，一堆混合币种是加不出总额的。

代价，写在这里免得将来当成 bug：**买家在购物车看到 €184、进结算页变成 $200，会有一次跳变。** 所以那行小字必须放在结算页金额正下方，不能藏在角落。

### 2.4 后端下发的汇率已经以本币为基准

API 返回的是 USD 基准表。**后端负责换算成「以站点本币为基准」再下发**，前台只做一次乘法。

前台不需要知道 USD 中转这回事，也就不会出现「前台自己算错方向」这类 bug。而且只下发 `currencies` 里那几个，不是 166 个——一个只开 3 个币种的站没有理由让每个访客下载 166 条汇率。

## 3. 数据模型

### `u_s_rate` — 汇率，单行表

```sql
CREATE TABLE IF NOT EXISTS `u_s_rate` (
  `id`           tinyint      NOT NULL DEFAULT 1   COMMENT '恒为 1。和 u_s_siteinfo 一样，这张表只有一行',
  `base_code`    varchar(10)  NOT NULL DEFAULT 'USD' COMMENT '⚠ 这是 API 返回值的基准，跟着汇率源走，不是站点本币。站点本币在 u_s_siteinfo.currency',
  `ratesjson`    mediumtext   COMMENT '自动拉回来的完整汇率表，{"CNY":6.728426,"EUR":0.860364,...}。整体读整体写',
  `overridejson` varchar(1000) COMMENT '运营手工覆盖，同样以 base_code 为基准。填了就压过 ratesjson，逐币种生效',
  `fetchtime`    datetime     COMMENT '最后一次成功拉取的时间。管理台显示「汇率更新于」，也是判断过不过期的依据',
  `fetchstatus`  varchar(20)  COMMENT '成功/失败。最后一次拉取的结果，管理台标红用',
  `fetcherror`   varchar(500) COMMENT '失败原因，排查用。成功时清空',
  `updateuser`   varchar(50)  COMMENT '最后改覆盖值的人',
  `updatetime`   datetime     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='汇率表，本库只有一行';
```

**为什么是单行 JSON 而不是 166 行**：永远整体读、整体写，没有任何按币种查询的场景，拆行只会多出 166 次 insert 和一堆没人看的行。和 `u_s_siteinfo.contentjson` 的做法一致。

### `u_s_siteinfo` 加一列

```sql
ALTER TABLE `u_s_siteinfo`
  ADD COLUMN `currencies` varchar(200) DEFAULT NULL
  COMMENT '前台允许买家切换的币种，逗号分隔，如 USD,EUR,CNY。留空=不显示切换器。⚠ 与 currency 不是一回事：currency 是基准（商品价格用它存），这一列是买家能切到哪些';
```

⚠ **`currency` 和 `currencies` 会被看错**，列注释必须写清楚。基准币种由后端自动并入可选列表，运营不填它也不会把买家锁在外面。

## 4. 后端

### 4.1 `RateFetcher` — 定时拉取

`station-console` 现在**没有** `@EnableScheduling`，主类要加。

- 每天 01:30 拉一次（API 是 UTC 00:0x 更新，留足余量），外加启动后延迟 30 秒拉一次；
- 用 JDK 自带的 `java.net.http.HttpClient`。**不引任何 HTTP 库**——`CosClient.java` 就是这么写的，`pom.xml` 顶部也明写「OkHttp 一个都不引」；
- 超时 10 秒；
- **失败不抛异常**。写 `fetchstatus=失败` 和 `fetcherror`，`ratesjson` 保持上一次的值。一个汇率接口超时不该让任何东西停下来。

启动时那次用延迟而不是 `@PostConstruct`：`@PostConstruct` 会把一次网络请求塞进启动路径，API 慢的时候整个服务起不来。

### 4.2 `RateService` — 取值与换算

```
effectiveRates()  = ratesjson 叠加 overridejson（覆盖优先）
rate(from, to)    = rates[to] / rates[from]
```

两个都相对 `base_code`，所以任意两个币种都能交叉算出来——站点本币是 CNY 也不用换汇率源。

进程内缓存 + `evict()`，与 `SiteInfoService` 同构（`volatile` 字段，写操作后失效）。⚠ 这意味着**直接改库不生效，要重启或经由管理台保存**，和 `u_s_siteinfo` 的现有约定一致，别做成两套。

### 4.3 `/openapi/site/info` 增加三个字段

```json
"currencies": ["USD", "EUR", "CNY"],
"rates":      { "USD": 1, "EUR": 0.860364, "CNY": 6.728426 },
"rateTime":   "2026-09-08T00:02:31Z"
```

> ⚠ **键名是 `rateTime`（驼峰），不是本文原来写的 `ratetime`。** 2026-09-18 核对代码订正：
> `SiteOpenService.java` 下发的是 `"rateTime"`，前台类型 `useSite.ts` 读的也是这个键。
> 这里写错会直接误导对接的人，所以特意留一条。

`rates` 已经是**以站点本币为基准**的（见 2.4），前台直接乘。`currencies` 第一个恒为基准币种。

前台因此不需要额外发请求——这个接口本来就是首屏必拉的。

### 4.4 管理台接口

- 「买家可选币种」并入现有的 `PUT /api/site`（`currencies` 字段），权限沿用 `site:station:edit`；
- 汇率状态与手工覆盖：`GET /api/rate`、`PUT /api/rate`，同样 `site:station:edit`。
  > 2026-09-18 补记：实际还多了一个 **`POST /api/rate/refresh`**（管理台手动触发一次拉取），
  > 本文当初漏记。

## 5. 前端

### 5.1 前台 `station-site`

**语言下拉（`SiteHeader.vue`）**

⚠ **面板内容用 `v-show`，不能用 `v-if`。** SSR 输出里必须包含全部语言的 `<a href>` 和 `hreflang`，只是视觉上折叠。改成 `v-if`、或者换成 JS 跳转，等于把现在的多语言 SEO 直接扔掉——而且这种损失在页面上完全看不出来，只会体现在几个月后的收录量上。

触发器显示当前语言名（复用现有的 `NAMES` 表）。要支持点击外部关闭和键盘可达。

**币种切换器（新组件 `CurrencySwitcher.vue`）**

- 只在 `site.currencies.length > 1` 时渲染，和语言切换器「只开一种就不显示」的现有行为一致；
- 选中值存 Cookie `SITE_CURRENCY`（`useCookie`，Nuxt 内置、SSR 安全），一年有效期，`sameSite: lax`；
- 放在语言切换器旁边。

**`useDisplayCurrency()`（新 composable）**

读 Cookie → 校验是否在 `site.currencies` 里（不在就静默回落本币）→ 暴露 `display(amount)`。

**价格渲染点要逐处判断，不能全局替换：**

| 文件 | 传的币种 | 处理 |
|---|---|---|
| `components/ProductCard.vue` | `props.item.currency`（逐商品） | **换算**。被 `pages/index.vue` 和 `pages/products/index.vue` 复用，改这一个就覆盖了首页和列表页 |
| `pages/products/[code].vue:55` | — | **先修，再换算**，见下 |
| `pages/cart/index.vue` | `site.currency` | **换算** |
| `pages/checkout/index.vue` | `site.currency` | **本币**，加「≈ €184.00，最终以 USD 为准」 |
| `pages/orders/index.vue` | `order.currency` | **本币**（订单已落库，那一列就是本币） |
| `pages/orders/[id].vue`（3 处） | `order.currency` | **本币** |
| `pages/account.vue` | `site.currency` | **本币** |

⚠ `lib/shop.ts` 的 `formatMoney` **本身不改**。它的职责是「给定金额和币种，格式化」，换算发生在调用它之前。把换算塞进 `formatMoney` 会让订单页那几处也被连带换算掉，而它们必须是本币。

**先修商品详情页。** `pages/products/[code].vue:55` 现在是 `` `${product.currency} ${product.price}` `` 直接拼串，压根没走 `formatMoney`——所以详情页显示的是「USD 100」而不是「$100.00」，日元还会带上不该有的小数位。这是这次动工之前就存在的不一致，但**不修它，详情页就会是全站唯一不参与币种换算的页面**，而这恰恰是买家最可能停留、最需要看到本地币种的一页。改成和别处一样调 `formatMoney`，再接上换算。

### 5.2 管理台 `station-console-ui`

站点概览的「站点设置」卡片加一项「买家可选币种」，复用刚做的语言那套多选逻辑（候选来自 `utils/currency.js` 的 `currencyOptions`，越界当场标红、保存时剔除）。

新增一块汇率区：最后更新时间、当前生效汇率表、拉取失败标红、手工覆盖的小表格。**汇率超过 7 天没更新要标红**——免费 API 静悄悄挂掉是最可能的故障，而它在页面上没有任何其他症状。

## 6. 降级与出错

| 情况 | 行为 |
|---|---|
| API 拉取失败 | 继续用上次的 `ratesjson`；管理台能看到失败状态和原因 |
| 从来没拉成功过 | `rates` 只含本币，前台不显示切换器——**降级成现在的样子** |
| Cookie 里的币种已被运营从 `currencies` 删掉 | 静默回落本币 |
| `overridejson` 里有非法值 | 忽略该条 + WARN，不影响其它币种 |
| 汇率超过 7 天没更新 | 管理台标红；**前台不阻断**——有旧汇率也比没价格强 |

## 8. 怎么验

**换算数学**
- 站点本币设成 CNY（非 USD），验证 `CNY→EUR` 等于 `rates[EUR]/rates[CNY]`。这是最容易写反的一处。
- 手工覆盖 EUR 之后，EUR 走覆盖值、CNY 仍走自动值。

**SSR（这两条是这个功能的核心风险）**
- 带 `SITE_CURRENCY=EUR` 的 Cookie `curl` 首页，**返回的 HTML 里直接就是 €**，不是先 $ 再由 JS 跳。
- `curl` 首页，输出里能 grep 到全部 8 个 `hreflang` 链接——语言下拉不能把它们藏进 `v-if`。

**降级**
- 把 `ratesjson` 清空，前台应回落成只有本币、不显示切换器，页面不报错。
- 把汇率 API 的域名在服务器 hosts 里指向黑洞，拉取失败时 `/openapi/site/info` 响应时间不受影响。

**下单链路**
- 选 EUR 浏览 → 加购 → 结算页金额是本币且带换算提示 → 提交后 `u_s_order.currency` 是本币。

**四个页面同一件商品要显示同一个价格**
首页、商品列表、商品详情、购物车。详情页最容易漏——它原来根本不走 `formatMoney`，是这次才接进来的。
