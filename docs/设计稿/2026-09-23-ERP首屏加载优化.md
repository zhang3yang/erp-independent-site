# ERP 首屏加载优化（gzip_static + 入口包拆包）

**状态**：**nginx 部分已上线并验收通过**（2026-09-23 16:49）；前端 dist 拆包待下一次发版
**起因**：`console.erp.vclinker.com` 冷缓存打开登录页要等约 20 秒，用户报"页面加载慢"。
**结论**：不是接口慢，是 nginx 把 1.79 MB 的入口 JS 原样不压缩发出去，而机器出口带宽只有约 1 Mbps。

---

## 一、实测（改之前的线上）

用 `tools/check-console-erp-cache.mjs` 量出来的，不是估算：

| 步骤 | 资源 | 传输 | 耗时 | 备注 |
| --- | --- | --- | --- | --- |
| 1 | `/login`（= `index.html`） | 5 KB | 0.15 s | |
| 2 | `static/js/index-UahnCZcd.js` | **1,746 KB** | **14.6 s** | 入口包，`content-length: 1788693`，无 `content-encoding` |
| 3 | `static/css/index-h9XRzmN4.css` | **457 KB** | **4.7 s** | 同样没压缩 |
| 4 | `login-*.js` 路由分片 | 64 KB | 0.14 s | |
| 5 | `data.erp` 的 `captchaImage` / `getConfig` | 4 KB | 0.2 s | |
| | **合计** | **2,204 KB** | **约 17.6 s** | 下载速率稳定 120–130 KB/s（≈ 1 Mbps 出口上限，不是抖动） |

首屏两个文件占掉 19 秒里的 19 秒。

## 二、根因

**1. nginx 没开压缩，而压缩包早就打好了。**
线上 `C:\nginx\conf\nginx.conf` 的 `http{}` 里 `gzip on;` 是注释掉的，也没有 `gzip_static`。
而 `C:\wczlerp\web\dist` 里 `.gz` 文件一直都在——`vite-plugin-compression` 按
`VITE_BUILD_COMPRESS=gzip` 打的：

| 磁盘上的文件 | 关键数字 |
| --- | --- |
| `static/js/index-*.js` | 1,788,693 字节 |
| `static/js/index-*.js.gz` | **583,170 字节**（就在旁边，没人用） |
| `static/css/index-*.css.gz` | 66 KB |
| `index.html.gz` | 1,398 字节 |

**2. 出口带宽约 1 Mbps。** 82.156.158.174 的出口实测 120–130 KB/s，这是硬天花板，
任何几百 KB 以上的文件都会被它卡住。压缩只能缓解，不能突破。

**3. 入口包太胖。** `main.js` 把 Editor（拖进 quill）、FileUpload、ImageUpload 全局注册，
加上整包 element-plus 及其全量 CSS，全部打进入口。`vite.config.js` 没有 `manualChunks`，
于是登录页为了渲染一个账号密码框，必须先下完整个 ERP。

次要两条（顺手改了）：静态资源没有 `Cache-Control`，每次访问都回源校验；
`listen 443 ssl` 没开 http2。

## 三、改了什么

### 3.1 nginx（零代码改动，收益的绝大部分）

配置在 **`deploy/nginx/erp/nginx.console-erp.conf`**（可直接粘贴的完整版本）：

- `http{}` 加 `gzip_static on;` + `gzip on;`（含 `gzip_types` / `gzip_vary` / `comp_level 6`）
- console.erp 的 `listen 443 ssl` 改 `listen 443 ssl http2`
- `location /static/` 加 `expires 1y` + `Cache-Control: public, immutable`
- `location = /index.html` 加 `Cache-Control: no-cache`（**这一条不能省**，理由见 §六.2）
- `location = /favicon.ico` 加 `expires 30d`

### 3.2 前端（`RuoYi-Vue3`）

| 文件 | 改动 | 为什么 |
| --- | --- | --- |
| `src/main.js` | Editor 从 `import` + 同步注册改成 `defineAsyncComponent(() => import('@/components/Editor'))` | 全仓只有 `views/system/notice/index.vue` 一处用 `<editor>`，登录页一处都不用，却要背 quill 的重量 |
| `vite.config.js` | `build.rollupOptions.output.manualChunks`：`vue` 全家桶 → `vendor-vue`，`element-plus` → `vendor-element-plus` | 让这两坨的 hash 与业务代码无关，发版不会失效（**不是**为了首屏变小） |

⚠ `manualChunks` 里**故意没有**"其它 node_modules 全丢一个 vendor"的兜底分支：
入口会因此依赖那个 vendor，`echarts` / `vuedraggable` 这类只有懒加载页面才用的库会被
拽回首屏，反而变慢。没点名的一律 `return undefined`，交给 rollup 自己决定。

### 3.3 附带修掉的隐患

`RuoYi-Vue3/src/components/BusinessShopSelector/index.vue` 行尾是混合的
（70 个 CRLF + 1 个 LF）。它不影响功能，但会让本地构建与线上构建的 `data-v-*`
不一致（见 §六.1），值得顺手统一。

### 3.4 ⚠ 关于本次打好的那份 dist 包

`C:\build\web-dist.zip`（构建于 2026-09-23 15:59）**不只包含本次优化**：
当时另一个会话正在同一个工作区里改 RuoYi-Vue3（15:57 落了 5 个文件），
于是这个包把它们一起带上了——

| 文件 | 被带上的改动 |
| --- | --- |
| `.env.production` | `VITE_APP_TITLE`：众联ERP系统 → **管理后台**（标签页标题） |
| `src/settings.js` | 底部版权去掉「众联ERP」 |
| `src/views/index.vue`、`.env.development`、`.env.staging` | 同批品牌文案 |

这些改动**没有提交**（`git status` 里还是 M），而且不在本次优化范围里。
如果不想把它们一起发上去：等那边改完并提交，重新 `npm run build:prod` 再打包；
或者只发 nginx 那部分（见 §四的"只上 nginx 压缩"一列，收益的绝大部分都在那里）。

## 四、账

首屏 = `index.html` 实际引用的所有 js/css（含 `modulepreload`），按 gzip 后的字节算。

| | 改之前 | 只上 nginx 压缩（**已上线**） | 再叠加拆包（**待发版**） |
| --- | --- | --- | --- |
| 入口 js | 1,746 KB raw / 569 KB wire | — | **349 KB raw / 126 KB wire** |
| `vendor-element-plus.js` | （在入口里） | — | 1,033 KB raw / 322 KB wire |
| `vendor-vue.js` | （在入口里） | — | 252 KB raw / 94 KB wire |
| 入口 css | 457 KB raw / 64 KB wire | — | 46.7 + 14.6 = **61 KB wire**（拆成两个） |
| **首屏传输** | **2,204 KB** | **633 KB** | **604 KB** |
| **按 125 KB/s 估算** | **17.6 s**（线上实测 19 s） | 5.1 s | **4.8 s** |

**要看清的一件事**：拆包本身只让首屏少了 0.3 秒。它的价值在**缓存**——
`vendor-vue` + `vendor-element-plus` 共 416 KB wire，发版时 hash 不变，
配 `immutable` 之后二次访问完全不下；不拆的话每次发版都要重下整个入口。
quill（203 KB raw / 61 KB gzip）也移出了首屏，只有打开「通知公告」才下载。

## 四bis、线上落地记录（2026-09-23 16:49，已验收）

**怎么落地的**：这台 ERP 服务器**没有 sshd、22 端口从来没开过、腾讯云账号也不在开发机这边**，
所以走的是"人在远程桌面里跑脚本、开发机在这边验"：`deploy/scripts/step7-erp-nginx-gzip.ps1`
（备份 → 加 gzip → 加 http2 → 加缓存头 → `nginx -t` → 不过就自动还原），确认
`RESULT: CONFIG OK` 后人工 reload。

**实测（`node tools/check-console-erp-cache.mjs`，11 项全过）**：

| 检查 | 结果 |
| --- | --- |
| `/login` | 200，`cache-control: no-cache`，**1.4 KB**（gzip 前 5.3 KB） |
| HTTP/2 | ✅ ALPN 协商出 `h2` |
| `index-UahnCZcd.js` | `content-encoding: gzip`，**1,746.8 KB → 569.5 KB**，`immutable` |
| `index-h9XRzmN4.css` | `content-encoding: gzip`，**457.4 KB → 64.0 KB**，`immutable` |
| 内容完整性 | gzip 解压后与原始文件 sha256 **逐字节一致**（1746.8/457.4 KB 两个都过） |
| **首屏传输** | **2,204.1 KB → 633.5 KB，约 17.6 秒 → 约 5.1 秒** |

**过程里值得记住的三件事**：

1. **这台机器上的 nginx 必须 `cd C:\nginx` 再执行**（`-t`、`-s reload`、`-V` 都一样）。
   它按当前目录找 `conf/nginx.conf` 和 `logs/`，在别处跑会报
   `[emerg] CreateFile() "C:\Users\Administrator/conf/nginx.conf" failed`。
   第一次落地就在这里失败了一轮——**脚本的自动还原当场生效，线上配置没被写坏**。
   手册 §8.2 本来就是这个写法，是本节初稿写错了。
2. **脚本是值钱的**：不仅因为 `console.erp` 在配置里出现两次（80 + 443）、`data.erp`
   还有一个一模一样的 `listen 443 ssl;`，还因为 `nginx -t` 失败时它会自己还原。
   （本地拿快照空跑时它还抓出一个真 bug：第一版按"第一个 `server_name console.erp`"
   定位，命中的是 80 那个块。）
3. **校验脚本自己也踩了 gzip 的坑**：gzip 一开，`/login` 响应也变成 gzip，
   脚本原来按明文解析 `index.html` 就解析不出资源引用了。凡是要读内容的地方都得
   先看 `content-encoding`——这条已经写进脚本注释。

## 五、怎么验

```bash
# 在任意能访问 console.erp 的机器上（只读，不改任何东西）
node tools/check-console-erp-cache.mjs --local RuoYi-Vue3/dist
```

它检查：`/login` 是否 `no-cache`；每个 `/static/` 资源有没有 `content-encoding: gzip`、
有没有 `immutable`；**gzip 解开后与本地构建产物 sha256 是否一致**（这一条能抓出
Windows 上 `sendfile` + `gzip_static` 可能的截断——只看 `Content-Length` 看不出来）；
最后打出首屏传输账并与本次基线（2,204 KB）对比。改之前跑过一次：8 项过 3 项。

## 六、两个值得记住的坑

### 1. 本地构建和线上构建的 hash 永远对不上，但这不代表源码不同

现象：线上是 `index-UahnCZcd.js`（1,788,693 字节），本地从干净 HEAD 构建出来是
`index-BoMD8AYt.js`（1,788,303 字节）；CSS 更奇怪——**字节数完全相同（468,327）但 sha256 不同**。

原因：Vue SFC 的 scopeId 是 `sha256(相对路径 + 文件源码).slice(0,8)`（生产构建，
见 `@vitejs/plugin-vue` 的 `createDescriptor`）。所以**行尾**（CRLF / LF）一变，
scopeId 就变，进而 CSS、JS 内容都变，chunk hash 跟着全变——即使代码一字未改。
线上那套是在 CRLF 的检出里构建的。

怎么确认"线上就是 HEAD"而不是别的版本：拿线上 CSS 里的 `data-v-*` 反查。
把 `src` 下每个 `.vue` 按 LF 和 CRLF 两种行尾各算一遍 scopeId，线上 21 个 id
全部能对上现有源码文件，且与本地只在行尾上互补。→ 同一份源码，放心替换。

推论：**不要拿"文件名/hash 不一样"当作"线上代码不一样"的证据**，会白查一轮。
反过来也一样：替换 dist 之后所有 chunk 名字都会变，这是正常的，不是构建出错。

### 2. 给静态资源加 `immutable`，就必须同时让 `index.html` 不缓存

`index.html` 里写的是带 hash 的资源名。它一旦被浏览器缓存住，发版后用户会拿着
**旧入口**去要已经被换掉的 chunk，页面直接白屏。所以两份配置必须成对出现：

```nginx
location = /index.html { add_header Cache-Control "no-cache"; }   # 每次回源校验
location /static/      { expires 1y; add_header Cache-Control "public, immutable"; }
```

用 `location =`（精确匹配）而不是 `location /`：`try_files ... /index.html` 的最后一项
是内部重定向，会重新走一遍 location 匹配，所以 `/login`、`/system/user` 这些 SPA 路由
拿到的也是这一份不缓存的 index.html，不用逐条再写。

## 七、还没做的（按收益排序）

| 事项 | 能省 | 为什么没做 |
| --- | --- | --- |
| **element-plus 按需引入** | 首屏 604 KB → 约 330 KB（4.8 s → 2.6 s） | `vendor-element-plus.js` 是全量引入（322 KB wire），占了首屏一半。改成 `unplugin-vue-components` + `ElementPlusResolver` 是**运行时风险改动**：`v-loading` 指令、`ElMessage` 这类服务式组件、`app.use(ElementPlus, {locale, size})` 的全局中文语言包和尺寸都要单独接上，漏一个就是页面级故障。需要在浏览器里逐页点过才敢上生产，单独一次做 |
| **出口带宽 1 Mbps → 5 Mbps**（腾讯云控制台）或 dist 上 COS + CDN | 4.8 s → 约 1 s | 这是硬天花板，压缩只能缓解。控制台操作，不在本轮范围 |
| `ssl_protocols` 去掉 TLSv1/1.1 | 0 | 与"让页面变快"无关，单独改好回退（`nginx.production.conf`「已知问题 ②」） |
| Brotli（`.br` 比 `.gz` 再小约 15%） | 约 90 KB | 官方 Windows 版 nginx 不带 brotli 模块，要换构建 |
