# 在线咨询（买家 ↔ 运营实时对话）设计

日期：2026-09-04
涉及：`station-site`（Nuxt 前台）、`station-console-ui`（管理台）、`station-console`（后端）、`sdsstation`（库）

---

## 1. 要做的东西

前台和管理台各有一个右下角悬浮小圆圈，点开是一个对话窗口。买家在前台问，运营在管理台回，两边都能看到对方的消息。

一句话范围：**一个买家一条会话线程，运营在一个面板里处理所有线程。**

不做的（一期）：文件/图片消息、表情、「对方正在输入」、会话转接、机器人自动回复、聊天记录导出。这些每一个都能单独成篇，现在只有名字。

---

## 2. 三个已定的决定

### 2.1 匿名就能聊，邮箱选填

前台**不挡登录**。这不是省事，是这个站已经定下来的立场：`useBuyer.ts` 和 `cart/index.vue` 的页头都写着「挡一道登录会掉单，外贸站尤其如此」，询盘和下单都不要求账号——聊天没有理由比它们更严。

- 匿名访客靠一个 `CHAT_VISITOR` Cookie 认线程。
- 窗口里有一句「留个邮箱，我们回复时能通知你」，**选填**。填了就走现成的 `SiteBuyerService.resolveByEmail`，把这条会话挂到 `u_s_buyer` 客户档案上。
- 已登录的买家（有 `BUYER_SESSION`）自动带身份，换设备也能看到历史。

代价，写在这里免得将来当成 bug：**没留邮箱的人清了浏览器数据就找不回对话，运营也没法邮件回访。** 这是选「不挡登录」换来的，不是缺陷。

### 2.2 轮询，不上 WebSocket

窗口开着 3 秒拉一次增量（带 `sinceId`），收起时只拉未读数（前台 30 秒 / 管理台 15 秒）。

选它的理由是**部署面为零**：nginx 配置、`start-console.bat`、安装脚本一个字都不用改，掉线自愈，将来多实例也不需要 Redis 广播。代价是最差 3 秒延迟——一个外贸站同时在聊的不会超过几个人，这个延迟没人感觉得到。

⚠ `document.visibilityState === 'hidden'` 时**必须暂停轮询**。不加这条，买家开着的后台标签页会整天打服务器，而这种负载在日志里看起来像正常流量，很难查。

### 2.3 管理台只做悬浮球面板，不做导航页

面板是双栏：左边会话列表（未读置顶，按最后消息倒排），右边对话。运营在商品页、订单页都能随手回一句。

不做全屏的「在线咨询」导航页是 YAGNI：搜索、筛未读、看归档这些需求要等会话真的多起来才成立。加一页比改一页容易，等到了再加。

## 3. 数据模型

两张表，都在 `sdsstation`。沿用本库既有约定：`shop_code` 遗留列、`sitecode`、中文状态常量、小写无下划线的列名。

### `u_s_chat` — 会话线程，一个访客一行

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | |
| `shop_code` | varchar(50) | 【遗留列】 |
| `sitecode` | varchar(50) | 来自哪个站点 |
| `chatcode` | varchar(50) | `LT` + 10 位流水，走 `CodeGenerator` |
| `visitortoken` | varchar(64) | 32 字节 SecureRandom 的 base64url，就是 Cookie 里那个值 |
| `buyercode` | varchar(50) NULL | 留了邮箱或已登录才有 |
| `email` | varchar(150) NULL | 同上 |
| `name` | varchar(100) NULL | 访客填的称呼 |
| `lang` | varchar(10) NULL | 访客用哪种语言开的口——运营得知道用哪国话回 |
| `pageurl` | varchar(500) NULL | 他在哪个页面开的口，运营一眼看出他在看什么商品 |
| `clientip` / `useragent` | varchar(64) / varchar(500) | 排查用，和 `u_s_inquiry` 一致 |
| `lastmessage` | varchar(500) | 最后一条的摘要，列表直接显示不用 join |
| `lastmessagetime` | datetime | 列表默认按它倒排 |
| `consolereadid` | bigint DEFAULT 0 | 运营读到的最大 message id |
| `buyerreadid` | bigint DEFAULT 0 | 买家读到的最大 message id |
| `createtime` / `updatetime` | datetime | |

唯一键：`uk_chat_code (shop_code, chatcode)`、`uk_chat_visitor (visitortoken)`。
索引：`idx_chat_active (shop_code, sitecode, lastmessagetime)`。

### `u_s_chatmessage` — 消息

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | 自增，**同时是已读游标的取值** |
| `shop_code` | varchar(50) | 【遗留列】 |
| `chatid` | bigint | 指向 `u_s_chat.id` |
| `sender` | varchar(20) | `买家` / `运营`，中文常量，和 `SiteOrder.STATUS_*` 同风格 |
| `senderuser` | varchar(50) NULL | 哪个操作员回的（`u_s_user.username`）；买家侧为 NULL |
| `content` | varchar(2000) | 纯文本 |
| `createtime` | datetime | |

索引：`idx_msg_chat (chatid, id)`。

消息表上**不放 `sitecode`**：它由 `chatid` 决定，冗余一份就多一个会不一致的地方。

### 两个刻意的决定

**未读数现算，不存计数器。** `SiteBuyerMapper.xml` 顶部那条「累加的计数会漂，漏减一次就永远错下去」对聊天更成立。所以只存**已读游标**，未读数是

```sql
select count(1) from u_s_chatmessage
 where chatid = ? and id > ? and sender = '买家'
```

游标只增不减（`greatest(consolereadid, #{readId})`），并发下两个标签页同时标已读也不会把游标退回去。

**点开窗口不建行，发出第一条消息才建。** 呼应 `u_s_buyer` 的「没有『新建』按钮，就不会有一个对不上任何人的档案」——只是好奇点了一下小圆圈的人，不该在运营的会话列表里占一行。`POST /open` 在没有历史时只种 Cookie、回一个空列表，不写库。

## 4. 后端

### 4.1 两个新 Controller

买家侧 `SiteChatController` → `/openapi/site/chat/**`，**公开无门**，和询盘同一组：

| 方法 | 作用 |
|---|---|
| `POST /open` | 种 `CHAT_VISITOR` Cookie，回历史消息 + 未读数 |
| `GET /messages?sinceId=` | 增量拉取 |
| `POST /send` | 发一条（可带 `email` / `name` / `pageUrl` / `lang`） |
| `POST /read` | 推进 `buyerreadid` |

运营侧 `ConsoleChatController` → `/api/chat/**`，由 `AuthInterceptor` 管着：

| 方法 | 权限 |
|---|---|
| `GET /` 会话列表 | `site:chat:list` |
| `GET /unread` 总未读（红点用） | `site:chat:list` |
| `GET /{chatCode}/messages?sinceId=` | `site:chat:list` |
| `POST /{chatCode}/read` | `site:chat:list` |
| `POST /{chatCode}/send` | `site:chat:reply` |

### 4.2 三件做错了很难发现的事

1. **两个新 Controller 都要加进 `ApiExceptionHandler` 的 `assignableTypes`**（`ApiExceptionHandler.java:34`）。不加的话买家侧一个畸形参数就会给公网访客看到 Spring 的默认错误页（带类名和路径）——那正是 `OpenApiController` 当初被框进去的原因。
2. **`/api/chat/**` 每个方法都要挂 `@RequirePerm`**，`AuthInterceptor` 是默认拒绝，漏一个那个接口就是 403。
3. **新权限串要写进角色表**：迁移脚本 `UPDATE u_s_role` 给 `operator` 追加 `site:chat:list,site:chat:reply`。`admin` 是 `*`，不用动。

⚠ 但要知道：`console.grant-all-perms` 默认是 **true**（`application.yml:320`，`ConsoleProperties` 的 record 注释里写明了这是产品决定，不是疏忽）。这一项为真时，任何从 ERP 免密进来的人都拿 `*`，**上面那两个权限串不参与判定**——`@RequirePerm` 事实上是空的。

这不影响该怎么写代码（注解照挂，漏挂仍然是 403），但它决定了怎么验：把这一项配成 `false` 才看得到权限起作用。已经这样验过，见 §7 第 6 步。

### 4.3 访客令牌为什么在 Cookie 里而不是 URL 上

这个 token 是匿名会话的**唯一凭据**，拿到就能读走整条对话。放 query 参数（`?token=xxx`）会让它原样进 nginx 的 access log，日志谁都能看。

放 `CHAT_VISITOR` Cookie：`HttpOnly`（JS 读不到，XSS 偷不走）、`SameSite=Lax`（挡 CSRF）、`Secure` 跟随 `CONSOLE_COOKIE_SECURE` 配置、30 天。和本项目已有的两套会话（`CONSOLE_SESSION`、`BUYER_SESSION`）是同一种做法，不是新发明。

### 4.4 限流

新建 `ChatRateLimiter`，照 `InquiryRateLimiter` 写，Redis 键 `station:chat:rate:`，按 IP。默认放宽到 **20 条/分钟、500 条/天**——聊天本来就是一句句发，套询盘那个 5 条/分钟会把正常对话卡死。

### 4.5 XSS

消息两边都用 Vue 的 `{{ }}` 文本插值渲染，**不用 `v-html`**。后端存原文、不做 HTML 过滤：过滤会把买家问的 `<M8 螺丝` 这类内容吃掉，而渲染侧不解释 HTML 时，存原文是安全的。

## 5. 前端

### 5.1 前台 station-site

- `app/components/ChatWidget.client.vue` — 悬浮球 + 面板
- `app/composables/useChat.ts` — 状态、轮询、Cookie 之外的本地状态
- `app/app.vue` 挂一行 `<ChatWidget />`

`.client` 后缀 → 只在浏览器渲染，不参与 SSR。理由和 `useBuyer.ts` 里那条一样：每个访客各自的东西，收录没有意义，而 SSR 要把访客 Cookie 从 Nuxt 服务端转发给后端，是一整套额外的东西。

⚠ 文案要进 `useShopCopy.ts` 的 **8 种语言**（en/zh/ja/es/pt/ru/it/ko），约 14 个 key。这是前台的既有约定，也是这块工作量的大头。

### 5.2 管理台 station-console-ui

- `src/components/ChatDock.vue` — 挂在 `AppShell.vue` 里，**不是** `App.vue`：挂在 AppShell 里 `/login` 那个空页面上才不会冒出一个聊天球。
- `src/api/console.js` 加 5 个函数
- 按钮和输入框挂 `v-hasPermi="['site:chat:reply']"`

## 7. 怎么验

1. 跑迁移，确认两张表在、`operator` 角色的 `perms` 里有那两个新串。
2. 起后端 + 两个前端。
3. 前台匿名发一条 → 管理台悬浮球出红点 → 运营回一条 → 前台 3 秒内看到。
4. 前台留邮箱 → 客户管理里能看到这个人的档案（`resolveByEmail` 挂上了）。
5. 把前台标签页切到后台 → 网络面板确认轮询停了。
6. 用 `operator` 角色去掉 `site:chat:reply` → 回复按钮消失，直接打接口回 403。
