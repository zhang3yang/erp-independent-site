> （欧盟同意横幅还欠着，见 `SeoTracking.vue` 上那条提示）。而漏掉一条询盘
> = 漏掉一单，并且**漏掉是静悄悄的**——那才是这个站的营销里真正丢钱的地方。

这一份自己也查到了同样的事实——买家名单当时只有 5 个人、同意横幅欠着——

这一版当成了可以忽略的背景。**

### 这份文档留着的价值

1. **§2 那段发信通道的分析仍然成立**：线上是一个 QQ 个人邮箱，而它同时在发
   注册验证、找回密码、询盘通知。以后真要做群发，那个约束还在，别再推导一遍。
2. **几条设计决定值得复用**：退订名单独立成表（退订意愿要比买家档案活得久）、
   不做打开率（追踪像素今天已不可信）、发送权限只给 admin。
3. **实现时踩到的两个坑**记在 `633dad4f` 的提交说明里：新表排序规则必须是
   `utf8mb4_0900_ai_ci`（跨表比 email 会报 Illegal mix of collations，
   而这个错编译期和启动时都发现不了）、计数要按明细表重算不能自增。

### 什么时候可以重新捡起来

三个条件同时满足：买家名单到百级、欧盟同意横幅做完、发信换成企业邮或专业发信服务
（营销信和事务信分开通道）。在那之前重做一遍只会得到同样的结论。

## 1. 为什么不是优惠券

先排除最容易想当然的方向。

**这个站没有支付环节。** 订单上的 `paymentPref` / `shippingPref` 只是「倾向」不是
条款（`SiteOrder` 类注释写着），`inquireOnly` 是面议行数——价格常常压根不公开。
客人「下单」实际是提交一个询价请求。

所以满减、优惠券、秒杀在这里没有可作用的对象：**没有成交金额可以打折**。
做出来是三个不会有人点的菜单项。

外贸站真正的营销动作是**给询过盘、下过单的人发信**：新品到了、报价更新了、
展会见。这个站已经攒着一份买家名单（`u_s_buyer`，含邮箱），SMTP 也配好了
（发注册验证信和询盘通知）。所以这个模块做的是**邮件营销**。

---

## 2. ⚠ 最大的约束：发信通道是一个 QQ 个人邮箱

线上 `spring.mail` 指向 `2689858083@qq.com`（QQ 个人邮箱 + 授权码，
见 `station-console/application-mail.yml`，那个文件不进版本库）。

两件事必须写在最前面：

1. **QQ 个人邮箱的 SMTP 日发信量在几十封量级**，超了会被冻结。
2. **同一个邮箱在发询盘通知、注册验证信、找回密码。**

第 2 条是这整个设计的支点：**营销信把这个邮箱搞挂，站的命脉流程一起停**——
新买家注册不了（收不到验证信）、老买家密码找不回、询盘来了运营不知道。

用户 2026-09-09 的决定是「先做功能，严格限速跑在现有通道上」。所以：

### 事务信绝对优先，而且根本不走营销队列

| | 走哪条路 | 受配额限制吗 |
|---|---|---|
| 注册验证、找回密码（`BuyerMailer`） | 原来的直发路径 | **不受** |
| 询盘通知（`InquiryNotifier`） | 原来的直发路径 | **不受** |
| 营销群发（本模块新增） | 新的发送队列 | 受，而且只能用配额里**剩下**的 |

⚠ 实现上**不要**为了「统一发信入口」把 `BuyerMailer` / `InquiryNotifier` 改成
走新队列。那样做的第一个后果就是「营销任务占满配额 → 新用户注册收不到验证信」，
而这个故障在日志上看起来只是一句「配额用尽」，没人会把它和「注册不了」联系起来。

### 配额和节流

```
station.campaign.daily-quota    默认 30   一天最多发多少封营销信
station.campaign.interval-ms    默认 20000  两封之间隔多久
```

配额用完 → 任务**排队等明天**，不是失败。名单现在只有 5 个人，30 封的配额
完全够用；这两个数留成配置项是为了换企业邮之后能直接放量。

⚠ 配额按**自然日**算，不是滚动 24 小时。滚动窗口要记每封信的时间戳再回溯，
而这里要的只是「别把邮箱发爆」，自然日足够，且运营看得懂。

## 3. 数据

三张新表 + `u_s_buyer` 加一列。

### `u_s_campaign` —— 一次群发

```
campaigncode  varchar(50)   内部编码，CodeGenerator 发号（前缀 CAMP）
subject       varchar(200)  邮件标题
content       mediumtext    正文富文本。⚠ 对外发送前必须过 RichTextCleaner
lang          varchar(10)   这封信写的是哪种语言（只用于展示和筛选，不做翻译）
filterjson    varchar(1000) 收件人筛选条件，原样存下来（见 §4）
status        varchar(20)   草稿 / 发送中 / 已完成 / 已取消
totalcount    int           目标人数
sentcount     int           已发送
failcount     int           发送失败
clickcount    int           点击总次数
createtime / updatetime / createuser
```

### `u_s_campaign_target` —— 这次群发的每一个收件人

```
campaigncode  varchar(50)
email         varchar(150)
buyercode     varchar(50)   可空：以后可能给非买家发
token         varchar(64)   这一条的令牌，退订链接和点击追踪都用它
status        varchar(20)   待发送 / 已发送 / 失败 / 已跳过
sendtime      datetime
failreason    varchar(300)
clickcount    int
UNIQUE KEY (campaigncode, email)
```

⚠ **唯一键挡的是「同一批里同一个邮箱出现两次」**。五个买家里可能有两个人填了
同一个公司邮箱，那时候发两封一模一样的信，收件人会当成垃圾。

### `u_s_unsub` —— 退订名单

```
email       varchar(150)  PRIMARY KEY
source      varchar(50)   从哪次群发退的（campaigncode），或 'manual'
createtime  datetime
```

⚠ **独立于 `u_s_buyer`，不是在买家表上加一个标记位。** 退订的人可能后来删了账号、
又用同一个邮箱重新询盘，那时候会重新建一条买家档案——**退订意愿必须比买家档案活得久**。
在买家表上加标记的话，那一刻退订记录就没了。

### `u_s_buyer` 加一列 `lang`

```
lang  varchar(10)  这个买家提交询盘/下单时用的语言
```

前台在 `SiteOrderService.submit` / 询盘那条路径上本来就知道当前语言（`site.lang`），
只是建档时没存。加这一列对新买家零成本。

⚠ **已有的 5 条这一列是空的**，按站点默认语言算。不要回刷——没有依据可回刷，
瞎填一个比空着更误导。

## 4. 收件人怎么筛

筛选条件存成 JSON（`filterjson`），因为它会长，而且每加一个条件不该改表结构。

第一版支持四个条件，都能组合：

| 条件 | 依据的列 |
|---|---|
| 询过盘 | `u_s_buyer.inquirycount > 0` |
| 下过单 | `u_s_buyer.ordercount > 0` |
| 国家 | `u_s_buyer.country` |
| 语言 | `u_s_buyer.lang` |

### ⚠ 三条硬性排除，不受筛选条件影响

1. **在 `u_s_unsub` 里的**——退订了就是退订了
2. **`status` 是停用的**
3. **邮箱为空或格式不合法的**

这三条写在 SQL 里，不做成界面上的开关。做成开关就意味着有人能关掉它。

### 「先看看有多少人」

界面上选完条件先出一个人数，运营点「创建群发」才真的把这批人写进
`u_s_campaign_target`。**名单在创建那一刻定格**——之后新来的买家不会自动被加进
一个已经在发的任务里。

## 5. 内容：正文和商品卡片

### 正文走现成的白名单

`RichTextCleaner.clean()`，和博客正文、商品详情**同一条规矩**，不新造过滤器。
`<script>` / `<iframe>` / `<style>` / 事件属性 / `javascript:` 协议全部剥掉。

管理台那个输入框是纯文本域手写 HTML，没有所见即所得编辑器——和博客一样，
这也是那个清洗器敢不放行 `style` 的前提。

### 「插入商品卡片」

运营选几个商品，自动生成带图、带名称、带链接的段落插进正文。

**这是这个方案里最值钱的一块。** 外贸营销信最主流的形态就是「新品推荐」，
而让运营手写 HTML 去拼商品图和链接，这个功能就没人会用。

⚠ 生成的卡片是**纯内联样式的表格布局**，不是 flex/grid。邮件客户端（尤其 Outlook）
对现代 CSS 支持极差，flex 布局在 Outlook 里会整个塌掉。这一条不是保守，是邮件
HTML 的常识，写在代码注释里。

⚠ 商品图用**绝对地址**（`https://file.<域名>/...`）。邮件里没有「当前站点」这个
概念，相对路径就是死图。

## 6. 退订和点击追踪

### 退订链接，每封必带

```
https://<主域>/openapi/site/campaign/unsub?t=<target.token>
```

点了立刻写进 `u_s_unsub`，回一个「已退订」的确认页。

⚠ 令牌是**每个收件人一条**，不是每次群发一条——共用令牌的话，一个人退订会
把整批人都退掉。

⚠ 这不是合规摆设。收到垃圾投诉 → QQ 邮箱被封 → **询盘通知和密码找回一起废掉**。
退订链接是在保护那条命脉，不只是在守法。

### 点击追踪

正文里的链接改写成 `…/campaign/click?t=<token>&u=<原地址>`，记一次然后 302 过去。

⚠ `u` 参数必须校验：只允许本站域名下的地址。不校验就是一个开放重定向，
而且是从**邮件里**点出去的——那正是钓鱼最想要的跳板。校验规则和
`BuyerAccountController.safePath` 同一套思路。

### ⚠ 刻意不做打开率

打开率靠 1×1 追踪像素。而 Apple Mail 的隐私保护会**无条件预加载所有像素**
（全部显示成已打开），Gmail 走代理缓存。这个数字今天已经不可信。

为一份 5 人的名单新增一个追踪像素端点和隐私面，换一组假数据，不值。
**点击**不受这些影响，而且在 B2B 上更有用：「谁点了那个商品」是一条实打实的
销售线索。

## 7. 权限：发送只给 admin

| 权限 | 谁有 | 能干什么 |
|---|---|---|
| `site:campaign:list` / `query` | operator + admin | 看群发历史和效果 |
| `site:campaign:edit` | operator + admin | 建草稿、改内容、选收件人 |
| `site:campaign:send` | **只有 admin** | 点「发送」 |

**发信是不可撤销的对外动作**，和站长工具里「整站禁收录」同一个性质，归站长。

这和博客「五件套全给 operator」不同，**不是不一致**：文章发错了能改能删，
信发出去追不回来。

## 9. 验收

### 功能

1. 建一封信，选「询过盘」，人数出来是 1（当前库里 `inquirycount>0` 的只有 1 条）
2. 发送后 `u_s_campaign_target` 里那条是「已发送」
3. 点退订链接 → `u_s_unsub` 多一行 → **再建一次同样条件的群发，这个人不在名单里**
4. 点正文里的链接 → `clickcount` 加 1，且**真的跳到了原地址**

### ⚠ 安全断言（照站长工具那次的教训写）

**a. 正文富文本必须被剥干净。** 正文里粘：

```html
<p>ok</p><script>alert(1)</script><img src=x onerror=alert(1)>
```

发出去的邮件正文里 `<script>` 和 `onerror=` 必须是 0 次，
**而且 `<p>ok</p>` 必须还在**——只验第一条的话，「白名单配错把正文整段吃掉」
也会显示通过，那是假通过。

**b. 点击追踪不能变成开放重定向。**

```
/campaign/click?t=<真令牌>&u=//evil.com
/campaign/click?t=<真令牌>&u=https://evil.com
/campaign/click?t=<真令牌>&u=/\evil.com
```

三种都必须落回站内，不能跳出去。

**c. 退订令牌不能猜。** 用别人的 token 退订只能退掉那个人；
`t` 传空或乱填要拒绝，不能退掉任何人。

### ⚠ 验证时注意缓存

站长工具那次踩过：`SiteSeoService` 的缓存没有 TTL，直接改库不会生效，
导致安全断言**假通过**。本模块**不做配置缓存**，所以没有这个问题；
但如果以后加了，验证时必须走管理台接口改值，或者重启服务，不能直接 UPDATE 库。

## 10. 刻意不做

- **自动化触发**（询盘 N 天没成交自动发跟进信）。价值最高也最危险：没人看着的
  时候可能把整批人得罪光。名单只有 5 个人，攒不出判断依据。等名单上百再说。
- **A/B 测试、可视化编辑器**——现在是空转。
- **一封信写多个语言版本**。用户 2026-09-09 定的是「一封信一种语言，发给筛出来
  的人」，外贸实际上就是都发英文。`u_s_buyer.lang` 那一列是为了**筛选**，
  不是为了自动翻译。
- **打开率**，见 §6。
- **换发信通道**（企业邮 / 腾讯云 SES）。那是开通、验域名、配 SPF/DKIM 的活儿，
  不在代码这一侧。配额那两个配置项留着就是为了那天到来时直接放量。
