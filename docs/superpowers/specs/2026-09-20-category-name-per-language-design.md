# 站点分类的多语言显示名

## 目标

前台产品页侧栏的分类，现在**三种语言显示的文字完全一样**：

```
中文页 / 英文页 / 日文页：
    BATTERIES
    CABLE ASSEMBLIES
    PUMPS
    SILICONE PARTS
    加压疗法 ▾
      └ 腿部系统
```

因为 `u_s_sitegoods.sitecategory` 是主表上的一列自由文本，一份数据供所有语言共用。

本设计让它在前台**按当前语言显示各自的名字**，译名**照默认语言自动翻**，
不需要商家逐个语言手填；翻歪了在一张表里改。

## 不在范围内

只做站点分类。**规格型号、规格参数、站点商品图片、站点商品视频都不动**，
仍是所有语言共用。（这几项讨论过分语言方案，2026-09-20 决定先不做。
将来要做的话，加 `u_s_sitegoods_lang` 的对应列 + 同样的回退规则即可。）

商品名称、售价、起订量、单位、排序、上架状态、首页推荐保持共享。
组合已经是分语言的，不在本次改动内。

## 数据模型

### 新建一张站点级共享表

```sql
CREATE TABLE IF NOT EXISTS `u_s_sitecategory_lang` (
  `shop_code`  varchar(50)  NOT NULL DEFAULT '' COMMENT '【遗留列】不参与过滤',
  `sitecode`   varchar(50)  NOT NULL COMMENT '站点编码',
  `catkey`     varchar(100) NOT NULL COMMENT '分类路径的一级，取完整前缀。如 加压疗法、加压疗法/腿部系统',
  `lang`       varchar(20)  NOT NULL COMMENT '语言代码。⚠ 只存非默认语言，默认语言直接用原文',
  `name`       varchar(100) DEFAULT NULL COMMENT '该语言下的显示名。空或没有这一行 → 前台显示 catkey 最后一段原文',
  `createtime` datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updatetime` datetime     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`shop_code`,`sitecode`,`catkey`,`lang`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='站点分类的多语言显示名';
```

**迁移只有这一条 CREATE TABLE**，不动任何现有表、不迁任何现有数据。

### ⚠ `catkey` 存的是「路径的每一级」，不是整串

分类 `加压疗法/腿部系统` 拆成两行：

| catkey | lang | name |
|---|---|---|
| `加压疗法` | ja | 圧迫療法 |
| `加压疗法/腿部系统` | ja | レッグシステム |

**为什么不整串译一次**：大组「加压疗法」下面挂 5 个子分类的话，整串译就要把
「圧迫療法」这四个字在 5 行里各翻一遍、各存一遍，还可能翻出 5 种不同写法，
侧栏的组标题就飘了。逐级存的话大组只翻一次，所有子分类共用。

**为什么用完整前缀而不是光秃秃的一段**：`腿部系统` 可能同时挂在两个大组下，
语义未必相同。用前缀 `加压疗法/腿部系统` 让每个节点有唯一身份。

**翻译时的源文本是 catkey 的最后一段**（`加压疗法/腿部系统` → 只翻「腿部系统」），
不是整串——整串带着分隔符送给翻译接口，回来的东西不可控。

### 主表 `sitecategory` 一个字都不改

它继续同时充当三件事，改动面因此被压到最小：

```
"加压疗法/腿部系统"
   ├─ 筛选键（URL 的 ?cat=、后端 where sitecategory = / 前缀匹配）
   ├─ 两级层次的载体（靠分隔符 / ／ > ＞）
   └─ 没有译名时的兜底显示文字
```

译名只接管「显示文字」这一件。**URL 永远是原串，切语言不断链。**

## 自动翻译

### 触发时机

**一、保存商品时。** 算出该商品 `sitecategory` 的各级 catkey，对每个「站点已开启的
非默认语言」，若库里没有该 `(catkey, lang)` 行、或 `name` 为空，就调翻译补上。

- **已有译名永远不覆盖**（人工改过的、之前翻过的都保住）
- 分类没变且译名齐全时**一次翻译接口都不调**，所以日常保存不会变慢
- ⚠ **翻译失败不阻断保存**：记日志，商品照常保存，前台先显示原文，
  下次保存或在弹窗里点一下再补。保存商品和翻译分类是两件事，
  不能让腾讯云抖一下就让商家存不了商品

**二、「分类译名」弹窗里的「一键补齐」按钮。** 对全站所有分类做同样的事，
用于新分类没及时补上、或翻译当时失败的情况。

### ⚠ 源语言怎么定：本地判定，不依赖 API 自动识别

这个站的分类是**中英混着的**：`Silicone Parts` 是英文，`加压疗法/腿部系统` 是中文。
按「源语言 = 站点默认语言（zh）」一律处理的话，`Silicone Parts` 会被当中文翻，结果不可控。

判据放在本地，简单而确定：

```
这一段文本里有没有 CJK 字符？
  有  → 源语言 = 站点默认语言
  没有 → 源语言 = en
```

**为什么不用 `Source: "auto"`**：`SiteTranslateService.SUPPORTED` 目前不含 `auto`，
而腾讯云的**批量**翻译接口（`TextTranslateBatch`）是否接受 `auto` 我没有验证过——
单条接口接受不代表批量也接受。不拿没验证过的 API 行为当设计前提。
实施时若验证批量接口确实支持 `auto`，可以改用它，比本地判据更准。

⚠ **已知局限**：分类名要是用第三种语言写的（比如商家直接写了日文分类名），
会被判成「默认语言」而翻错。这种情况靠下面那张表手工改——这也正是修正入口存在的理由。

### 调用方式

复用现有的 `POST /site/translate`（`site:station:edit` 权限、语言白名单、
批量与字符数限制、密钥不出后端，全都现成）。按目标语言分批，一种语言一次调用，
把该语言缺的所有 catkey 一次送出去。

## 管理台交互

### 商品管理页加一个「分类译名」按钮

放在列表页工具栏（和「新增商品」同一排）。点开是一张表：

```
┌──────────────────────────────────────────────────────────┐
│ 分类译名                              [一键补齐] [保存]   │
├──────────────────────────────────────────────────────────┤
│ 分类（中文·默认）  │ en          │ ja        │ ko  │ ... │
├───────────────────┼─────────────┼───────────┼─────┼─────┤
│ Batteries         │ Batteries   │ バッテリー │ ... │     │
│ Pumps             │ Pumps       │ ポンプ     │ ... │     │
│ Silicone Parts    │ Silicone... │ シリコー.. │ ... │     │
│   └ ssss          │ ssss        │ ssss      │ ... │     │
│ 加压疗法           │ Compressi.. │ 圧迫療法   │ ... │     │
│   └ 腿部系统       │ Leg System  │ レッグ...  │ ... │     │
└──────────────────────────────────────────────────────────┘
```

- **行**：全站分类按层级展开去重后的所有 catkey，子级缩进显示
  （来源是 `select distinct sitecategory`，和前台侧栏同一个集合）
- **列**：站点已开启的语言。**默认语言那列只读**，显示 catkey 最后一段原文
- 单元格可直接编辑，空着就是「前台显示原文」
- **一键补齐**：只翻空格子，已填的不动

**为什么不放在商品编辑弹窗的语言页签里**：分类是全站共享的，
在单个商品里改会让人以为只影响这个商品。一张全站的表既符合它的真实作用域，
又能一眼看出哪个翻歪了。

### 商品编辑弹窗不动

「站点分类」还是原来那一个输入框，填的还是 `加压疗法/腿部系统`。
商家不需要知道译名表的存在——存完自动就有了。

## 接口

### 前台：只加字段，不改字段

`/openapi/site/info` 现有的 `categories` 是一个平铺字符串数组，**原样保留**，另加一个字典：

```json
"categories":    ["加压疗法/腿部系统", "Silicone Parts", "Silicone Parts/ssss"],
"categoryNames": { "加压疗法": "圧迫療法", "加压疗法/腿部系统": "レッグシステム" }
```

键是 `catkey`，值是当前语言译名；没译名的不出现在字典里。

这是**非破坏性变更**：发版窗口期里老前台配新后端照常工作，读不到 `categoryNames`
就显示原串。商品列表/详情接口一个字都不改。

### 管理台

```
GET  /api/site/categories/langs      读全站分类 × 各语言的译名（弹窗打开时）
POST /api/site/categories/langs      保存手工修改
POST /api/site/categories/translate  一键补齐（只翻空的）
```

## 写入语义

### ⚠ 只 upsert，绝不整份替换

译名是共享数据。保存商品时**只碰该商品分类路径涉及的那几个 `catkey`**，
不能像组合那样「提交的就是全部、库里多出来的删掉」——否则保存一个商品
会把别的分类的译名一起删掉。

弹窗的保存同理：提交哪几格就写哪几格。

### 改了商品分类之后，旧译名行留着不动

商家把商品从 `加压疗法/腿部系统` 改成 `Pumps`，前一个 catkey 的译名行就没商品用了。
**不清理**：那些行可能还被别的商品用着；就算真没人用也不碍事——
侧栏是从 `select distinct sitecategory` 出来的，没有商品挂着的分类根本不会出现，
孤儿行只是躺着，商家改回去还能直接复用。

## 校验

- `name`：`trimToNull` + 长度限制（100）。**不走富文本白名单**——它是纯文本，
  会出现在侧栏和面包屑里，不能按 `description` 那条路当 HTML 放行
- 语言白名单沿用现状：站点没开的语言不写库；默认语言不写库
- `catkey` 必须是**某个在库商品的 `sitecategory` 按分隔符切分后的某一级前缀**，否则拒绝。
  ⚠ 不能写成朴素的「字符串前缀」判断：那样 `加压疗` 这种切在字中间的值也会通过，
  往库里塞出一个永远不会被任何分类命中的孤儿行

## 前台改动

只有分类那块要动：

- `app/lib/categories.ts`：分组仍按 **key** 的段拆（保证同一大组永远归一组），
  显示时逐级查 `categoryNames`，查不到用原段。`categoryLeaf` 同理
- `app/pages/products/index.vue`：侧栏和页面大标题显示译名，**筛选仍传原串**，`?cat=` 不变
- `app/pages/products/[code].vue`：面包屑里的分类显示译名
- `app/composables/useSite.ts`：`SiteInfo` 类型加 `categoryNames`

## 发版顺序

```
迁移（建表）→ 后端 → 前台 → 管理台
```

**⚠ 后端必须在管理台之前**，否则管理台的译名弹窗调的接口还不存在。
前台早发晚发都安全（读不到 `categoryNames` 就显示原串）。

迁移脚本开头加幂等闸（查表在不在，在就 `RESULT: ALREADY APPLIED` 退出），
跑完手工补一条 `u_s_schema_migration` 台账。

首次上线后在弹窗里点一次「一键补齐」，把现有 6 个分类的译名灌进去。

|---|---|---|
| 1 | 建表后什么都不做 | 前台三种语言仍显示原文，**和改动前一模一样**（回归） |

| 3 | 英文分类 `Silicone Parts` 翻日文 | 按 en→ja 翻，不是当中文翻 |
| 4 | 中文分类 `加压疗法` 翻日文 | 按 zh→ja 翻 |
