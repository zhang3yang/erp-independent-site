# 金额按岗位可见 —— 方案

> **它回答一个问题**：怎么让销售看不到采购价、采购看不到销售价、仓库两样都看不到、财务全看得到。
> **它不回答**：菜单和按钮级的权限怎么配（那是 RuoYi 原生的角色管理，本方案只往里加两个权限点）。

**状态**：已实现（2026-09-10）。代码在 `RuoYi-Vue` / `RuoYi-Vue3`，迁移脚本是
`sql/migration/20260910_price_visibility.sql`。

落地时比本方案原先写的多出四处，都已随代码一起改掉，下面各节已就地更正：

| 多出来的 | 在哪 | 不做的后果 |
|---|---|---|
| `price:` 要进租户权限前缀白名单 | 3.4（新增） | 功能整体失效：商家侧拿不到这两个权限，所有人一律遮蔽 |
| 采购订单的预估/实际运费、套餐行的参考价 | 7.1 | 三个金额字段漏网 |
| 商品档案改单守卫 | 6.1 | 无权的人改库存预警量，参考价被<b>静默</b>抹掉 |
| 资金流水的金额要按业务类型遮 | 7.3 | 采购付款金额经 `/finance/transaction/biz` 漏到采购单详情页 |

## 0. 一句话

给系统加两个权限点 `price:cost` 和 `price:sale`，在**接口出口**把当前登录人无权查看的
金额字段写成 `null`，前端把对应的列整列不渲染；商家管理员在角色管理里按岗位勾选。

---

## 1. 现状与风险

货品单价、成本金额、销售价格、订单总额这些数字，现在对**任何登录用户全部可见**。
只要能进得了那个菜单，就能看到上面所有的钱。

具体的风险：

| 场景 | 现在会发生什么 |
|---|---|
| 销售打开库存或入库单 | 看得到采购价、成本价，等于知道公司的进货成本和毛利 |
| 采购打开销售订单或出库单 | 看得到卖给客户的价格 |
| 仓库打开任何单据 | 采购价和销售价一起看到，而他只需要数量 |
| 离职前导数据 | 一次性把价格体系带走 |

**只在前端把列藏起来是没有用的**。接口照样把数字发下去，浏览器按 F12 打开网络面板，
报文里明明白白。真要拦，只能拦在服务端。

## 2. 目标：谁该看到什么

| 岗位 | 采购价 / 成本 | 销售价 |
|---|:--:|:--:|
| 销售 | ✗ | ✓ |
| 采购 | ✓ | ✗ |
| 仓库 | ✗ | ✗ |
| 财务 | ✓ | ✓ |
| 平台超管 | ✓ | ✓ |

仓库两样都看不到，但**数量、批次、序列号、仓位一律照常** —— 他的活儿是管货不是管钱。

## 3. 权限模型

### 3.1 为什么不能按角色写死

这套系统的角色是**各商家自己建的**：`sys_role` 的主键是 `role_code` + 租户列 `shop_code`，
本地库里就有 9 个角色，名字五花八门。系统里根本不存在固定的
「销售 / 采购 / 仓库 / 财务」四个角色可以让代码去认。

所以只能走 RuoYi 原生那条路：**权限点挂在菜单上，商家管理员自己勾给自己的角色**。
登录时 `SysPermissionService.getMenuPermission` 把角色名下所有 `sys_menu.perms` 收集成一个集合，
判权就查这个集合。

### 3.2 两个权限点

```
price:cost   采购与成本价
price:sale   销售价
```

挂在一个**隐藏的父菜单**「价格可见性」下面（`menu_type='M'`、`visible='1'`），
不出现在侧边栏，只在角色管理的菜单树里出现，供勾选。

平台超管拿的是 `*:*:*`（`Constants.ALL_PERMISSION`），不受这两个权限约束。

### 3.3 为什么是两个，不是三个或四个

考虑过再拆出「单据合计金额」（让仓库能对账但看不到单价）和把「采购价 / 库存成本」
再分开，结论是**不值得**：

- 权限表越碎，配错的概率越高，而配错的后果正是这次要防的事；
- 「仓库看得到合计、看不到单价」听着合理，但一张单只有一行的时候，
  合计就是单价 —— 这层隔离是假的；
- 两个权限点刚好一一对应四种岗位（勾 sale / 勾 cost / 都不勾 / 都勾），
  再多一维就没有对应的岗位了。

需要更细的粒度时再拆，加权限点是向后兼容的。

### 3.4 ⚠ `price:` 必须进租户权限前缀白名单

这一条是实现时才发现的，**漏掉它整个功能就是失效的**，而且症状不指向原因：
菜单在库里、角色也勾上了，但商家侧的权限集里就是没有 `price:cost`，
于是所有人的金额全被遮蔽，看着像「代码写错了」。

商家（租户）的权限集不是直接取 `sys_menu.perms`，中间还过一道前缀白名单，
挡住 `system:` / `monitor:` / `tool:` 这些平台侧权限。这份名单有两个副本，两边都要加：

- `com.ruoyi.common.constant.TenantPermissionPrefixes` 的 `ALL` 和 `BUSINESS_ONLY`；
- `TenantShopMapper.xml` 里 10 处 `m.perms like '...'` 列表。

`price:` 是这份名单里唯一一个**没有页面**的前缀 —— 它只是两个纯权限点。
`BUSINESS_ONLY` 那半边同样要加，否则价格菜单挂不到商家菜单树上，角色管理里根本勾不到它。

## 4. 拦在哪里

```
                 ┌───────────────────────────────────────────┐
   数据库 ─────► │ Service                                   │
                 │   业务计算照旧用真实金额（成本核算、        │
                 │   毛利、库存金额都不能因为谁在看而变）      │
                 └──────────────────┬────────────────────────┘
                                    │
                 ┌──────────────────▼────────────────────────┐
                 │ ★ 序列化成 JSON 的那一刻                   │
                 │   按当前登录人的权限，把无权字段写成 null  │
                 └──────────────────┬────────────────────────┘
                                    │
                 ┌──────────────────▼────────────────────────┐
   浏览器 ◄───── │ 前端：对应的列整列不渲染                   │
                 │   （只是别留一排空格子，不承担安全职责）   │
                 └───────────────────────────────────────────┘
```

**关键点**：拦在序列化出口，不是拦在 Service 里，也不是拦在前端。

- 拦在 Service 里要改几十处查询，而且业务计算本身需要真实金额，容易改出错账；
- 拦在前端等于没拦；
- 拦在序列化出口只有一处代码，覆盖所有接口，且天然不影响内部计算。

## 5. 技术实现

### 5.1 照抄项目里已有的先例

`ruoyi-common` 里已经有一套一模一样的机制在跑：`@Sensitive` 注解 +
`SensitiveJsonSerializer`（基于 Jackson 3 的 `tools.jackson.*`），
用来做手机号脱敏，判据是「是不是管理员」。

本方案就是把判据从「是不是管理员」换成「有没有这个权限」，其余照搬。
**不引入任何新框架、新依赖。**

### 5.2 五个新增类

| 类 | 职责 |
|---|---|
| `PriceScope`（枚举） | `COST` / `SALE` / `AUTO`，各自带权限标识 |
| `@PriceField(PriceScope)` | 打在金额字段上的注解 |
| `PriceJsonSerializer` | 序列化时判权，无权就 `writeNull()` |
| `PriceMaskUtils` | 判权逻辑的唯一出处，序列化和改单守卫共用 |
| `PriceScopeAware`（接口） | 一列两用的字段自己说算哪一侧，见 5.4 |

用法就一行：

```java
@PriceField(PriceScope.COST)
private BigDecimal costPrice;
```

### 5.3 为什么写 null，不写 0 也不写 `***`

- 写 `0`：前端会当成「这单不要钱」参与合计，算出一堆假账；
- 写 `***`：塞不进 `BigDecimal` 类型的前端模型，得把整个字段改成字符串，牵连太广；
- 写 `null`：语义就是「这个值不给你」，而页面上那一列本来也整列藏掉了。

### 5.4 一列两用的字段怎么办

`u_f_docmain.totalamount` 这一列**销售出库单存的是销售额，其余单据存的是成本额**
（见 `DocumentServiceImpl` 里 `isSalesOutbound` 那一段）。同一个字段两种口径，
静态注解标不出来。

处理办法：标成 `PriceScope.AUTO`，让 `DocumentMain` 实现一个
`PriceScopeAware` 接口自己按 `docType` 说算哪一侧；序列化时用
`JsonGenerator.currentValue()` 拿到所在的对象回头问它。
判不出来（比如查询条件对象、`docType` 为空的草稿）就按最严的走：两个权限都有才给看。

全系统有两个字段需要它：`u_f_docmain.totalamount`，以及资金流水的 `amount`（按业务类型分成采购付款 / 销售回款，见 7.3）。

## 6. 四个必须提前想清楚的坑

这四条是实现时真撞上的，不是设想。**任何一条漏掉，这个功能就会从「安全加固」
变成「线上事故」。**（第四条见 3.4：`price:` 没进白名单，功能直接整体失效。）

### 6.1 看不见不能变成改没了 ⚠ 最危险

没权限的人拿到的价格是 `null`。他打开单据改个数量、改个仓库，一保存，
这个 `null` 原路回到后端，**把库里的价格冲掉了**。

必须在改单路径上补一条反向规则：**看不到的字段一律沿用库里的原值，
不认前端回传的 `null`**。

排查过全部改单入口，风险分布是：

| 入口 | 现状 | 要不要补 |
|---|---|---|
| 入库单 / 出库单改单 | 已经写着「传 null 就沿用原值」 | 不用 |
| 生产工单执行 | 已有 `feeOrExisting` 做同样的事 | 不用 |
| 采购订单改单 | 传 null 会当场报「采购单价不能为空」 | **要**（否则改数量都改不了） |
| 采购到货单运费 | 传 null 被 `nvl` 成 0，运费清零 | **要** |
| 销售订单改草稿 | 传 null 被当成 0，整单货款归零 | **要** |
| 商品档案改参考价 | `updateGoods` 无条件写 `standardprice`，校验又放过 null | **要**（⚠ 静默丢数据，连报错都没有） |

### 6.2 读和写对「没有登录上下文」的默认值必须相反

定时任务、内部调用、单元测试都跑在没有登录上下文的路径上。这时候：

- **读**：一律遮蔽。宁可少显示一次，也不能把价格漏出去；
- **写**：照收前端的值。压根没有要防的人，把内部调用的写入静默丢掉，
  是拿数据错乱换一个不存在的安全。

两边共用同一套判断的后果是实测出来的：采购发货单的运费在单元测试里被当场清零，
3 条测试挂掉才发现。

### 6.3 合计要跟着单价一起藏

单价列藏了、合计还挂在那儿，**一行一件的单子等于把单价直接写出来**。
前端隐藏时必须连带处理汇总行、`el-descriptions` 里的金额项，
不能只处理 `el-table-column`。

### 7.2 前端：17 个页面 + 1 个公共工具

公共工具是 `src/utils/price.js`，导出 `canSeeCost` / `canSeeSale` /
`canSeeBothPrices` / `canSeeEitherPrice` / `canSeeDocTotalAmount(docType)`。

```
components/  GoodsLineTable  GoodsSelectDialog  PartnerSelectDialog
库存         入库信息  出库信息  调拨信息  批次信息  库存台账  库存统计  商品信息
采购         采购订单  采购到货
订单         销售订单  销售退货  发货批次
生产         生产工单  生产单据
```

混着两种口径的列（出库列表的总金额）用 `canSeeEitherPrice`，不是整列藏掉：
服务端已经**逐行**按 `docType` 把无权的行写成 null 了，整列藏掉反而会把
他有权看的那几行一起藏了。

### 7.3 不动的地方

- **财务模块的页面**：菜单由 `finance:*` 权限管着，看不到菜单就看不到金额，再叠一层反而绕。

  ⚠ **但 `FinanceTransaction.amount` 仍然要遮**，原方案这一条判断错了：
  `/finance/transaction/biz` 是**故意**只按 `hasBusinessShop()` 放行的，好让没有 finance
  权限的业务员、采购员在自己的单据详情里看到款走到哪一步了（见 `FinanceTransactionController.biz`
  的注释）。采购付款的金额就是从这个口子流到采购单详情页上的。所以它标成 `AUTO`，
  由 `bizType` 决定：采购付款→成本侧，销售回款→销售侧，「其他」和账户余额 `balance`
  说不清归哪边，按最严的走；
- **业务计算**：成本核算、移动加权平均、毛利、库存金额一律用真实数字，
  不因为谁在看而变。

## 8. 上线策略

**脚本跑完的那一刻，行为必须和以前一模一样。**

一上来就把权限全收掉，所有人的价格列同时变空，看着就是系统坏了，
会淹在一片「怎么看不到价格了」的反馈里。

分两步：

1. **迁移脚本**：建两个权限点，然后**把它们发给现有的全部角色**。
   跑完之后谁也没受影响。
2. **收权**：商家管理员到「系统管理 → 角色管理」，按第 2 节那张表，
   给各个角色取消勾选。想什么时候收就什么时候收，可以一个角色一个角色地来。

以后**新建的角色默认不带**这两个权限，建角色的人自己按岗位勾 —— 那时候
系统里已经有这个概念了，不会误会。

回滚也简单：把两个权限重新发给所有角色即可，不需要回退代码。

## 9. 工作量与风险

| 项 | 实际 |
|---|---|
| 新增后端类 | 5 个（PriceScope / @PriceField / PriceJsonSerializer / PriceMaskUtils / PriceScopeAware） |
| 领域类打注解 | 21 个文件 50 个字段 |
| 改单守卫 | 4 处 |
| 权限前缀白名单 | Java 2 处 + TenantShopMapper.xml 10 处 |
| SQL | 1 个迁移脚本 + 基线补 27 行（3 菜单 + 15 角色授权 + 9 商家授权） |
| 前端 | 17 个页面 + 1 个公共工具 |
| 测试 | 23 条：14 条走真序列化（四种岗位、超管、通配权限、无登录、一列两用三种情形、只遮出不遮进），9 条覆盖四个改单守卫 |

**风险评级：中。**

- 机制本身很薄，只有一处判权逻辑，改错了是「全都看不见」这种一眼可见的故障，
  不会是悄悄算错账；
- 真正的风险集中在第 6.1 条（改单清零）—— 那是唯一会**动数据**的一环。
  四处守卫逐个写了测试；
- 前端 17 个页面是机械劳动，漏一处的后果是「某个页面还能看到价格」，
  安全上是缺口，但不会坏数据。

## 10. 已知边界与后续

1. **Excel 导出会绕过这套机制**。导出走 POI 和 `@Excel` 注解，不经过 Jackson。
   已核查：目前带金额的实体**一个导出口子都没有**（只有客户信息、日志、参数在导），
   所以眼下没有缺口。**以后要给单据加导出功能，必须在那里另挡一道**，
   这条要写进注解的文档注释里，免得后人踩。
2. **打印 / 单据模板**：同理，如果以后走服务端渲染 PDF，也不经过 Jackson。
3. **移动端 / 对外 API**：只要走同一套 Controller 就自动生效，无需额外处理。
4. **更细的粒度**：真需要「仓库能看合计不能看单价」这类需求时再加权限点，
   现有结构支持向后扩展。
