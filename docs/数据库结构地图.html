wczl-erp · 库表结构总览

wczl-erp 数据库地图

这套系统跑在 四个互不相同的库上：三个属于 ERP，一个属于独立站——而独立站那一个，每开一个站就单独一份、装在自己的服务器上。下面按库分册，讲清每张表存什么、哪几个字段是真正承载业务的，以及数据是怎么从一张单流到库存数字上的。

01 / 全景四个库，一条线

ERP 和独立站被刻意做成两个互不认识的系统：各自有库、各自有用户体系、各自能独立跑起来。它们之间只剩一条实线——从 ERP 点一下，免密进到某个独立站的后台。

02 / sdssys谁能用这套系统

这个库回答「你是谁、你属于哪个商家、你能点哪些按钮」。它是两套东西叠在一起：RuoYi 原生的 sys_* 用户体系，和后来加的 s_m_* / s_u_* 商家（多租户）体系。理解的关键是 shop_code——它是整个系统的租户键，几乎每张业务表的第一列都是它。

03 / sdsshop东西有多少

这个库存的是「现状」——不是发生过什么，而是此刻有多少货、在哪个仓、什么状态、值多少钱。加上定义这些货的主数据，以及正在进行中的采购单和生产工单。

主数据

所有库存动作的起点。主键 (shop_code, goodscode)。三个字段决定了这个商品在库存引擎里怎么被对待：

仓库树。waretype 区分实体仓和虚拟仓——车间、在途、待检这类「不是真仓库但要算库存」的地方用虚拟仓。

供应商、客户、内部部门共用一张表，靠 partnertype 区分。采购单、入库单上的「对方」指的就是它。

u_m_buyer销售客户主表

销售侧的客户档案，与 u_m_partner 是两套：这张更像 CRM（有星级、业务员归属、头像、店铺图）。u_m_buyer2 是它下面的二级客户（同一个客户的不同收货点/联系人）。

整个库存引擎的行为表。每种单据的方向（进/出/内部转换）、是否需要审核、是否允许负库存，都从这里读。详见下面的单据类型清单。

u_m_goods_partner商品供货关系派生

纯派生表，由已审核的采购入库单累积出来，用途只有一个：下次给这个商品开采购单时推荐供应商。记 inboundtimes 次数、lastcostprice 最近成本。

u_m_goods_position商品存放位置

库管员手写的大文本，「A 区 3 号架第 2 层」这种。不参与任何计算，只给找货的人看。

u_s_site独立站登记表（ERP 侧）

ERP 里「有哪些独立站」的名册。它不存站点的任何业务数据，只存怎么找到它、怎么跳进去。

sitecode 与站点库 u_s_siteinfo.sitecode 必须一致 domain 主域名，其余四个子域由它派生 consolesecret 跳转签名密钥，此处存 AES-GCM 密文 consoledomain 「进入管理」跳这里 status 管的是 ERP 发不发令牌，不是站点前台开关

库存现状：四象限模型

这是整个系统最值得先看懂的一件事。u_m_stock 的主键是五列：(shop_code, goodscode, warecode, qualityflag, onhandflag)。后两个 tinyint 组合出四种状态——所以同一个商品在同一个仓库里，最多会有四行，四行的数量各算各的。

u_m_stock实时库存汇总

当下有多少货、值多少钱。所有出入库最终都要落到这张表上。它有两个不同含义的「数量」，混淆它们是最常见的错。

physicalqty 物理库存，真实存在的数量 lockedqty 待审核出库单占用的量 reservedqty 【已废弃】原订单预占量，机制已取消，恒为 0，无代码读写
avgcostprice 移动加权平均成本 totalcostamount 库存总成本金额 version 乐观锁，并发扣减靠它
u_m_batchinfo批次信息

按批管理的商品，每次到货一个批次。主键含 batchcode + goodscode + warecode + 两个 flag，所以同一批次跨仓、跨象限也会拆行。

initialqty / remainingqty 到货量 / 剩余量 purchaseprice 批次当前成本单价 owner_orderdetailcode 专属批次：非空 = 这批货是为某条销售订单明细专门生产的，出库时只能发给它 expiredate / productiondate closedflag 关闭后不再参与挑批次
u_m_serial序列号明细

一物一码。每个序列号记住自己是怎么进来的、又是怎么出去的——入库单号和出库单号双向都留。

activeflag 1 在库 / 0 已出库 costprice 个别计价成本 indoccode / indetailcode / intime outdoccode / outdetailcode / outtime
u_o_reservation遗留表 · 原订单预占明细

订单预占机制已取消。这张表是遗留表：表和历史数据都还在库里，但没有任何代码读写，读它没有意义。原先它是 u_m_stock.reservedqty 的明细账——现在那个汇总列也恒为 0。别照着这张表去理解订单流程。

reservedqty 原「当前占用」，历史遗留值 releasedqty 原「已核销」 status 原 有效 / 已核销 / 已取消 shipcode / doccode 原核销去向

04 / 引擎单据 → 流水 → 库存

库存数字不是被直接改的。所有变动都走同一条三层管道，且分成两个时刻：建单只写单据，一个数字都不动；审核通过的那一刻，在同一个事务里写流水、改库存。

05 / sdsorder发生了什么

凡是「会一直长下去」的表都在这个库，并且按月拆表。MonthlyTableInitializer 在启动时和每天凌晨各跑一次，提前把当月和下月的表建好——请求链路上不建表，因为在业务事务里执行 DDL 会撞 MySQL 的 1412。

十一张月表，各自按不同的日期落表

这是查数据时最容易踩空的地方：决定一条记录落进哪张月表的日期列，每种单据都不一样。一张订单的多个发货批次完全可能落在不同月份的表里。

06 / sdsstation独立站，一站一库

每开一个独立站，就是一台服务器 + 一份 sdsstation 库 + 一套自己的用户体系。它与 ERP 之间没有任何外键、没有跨库查询；两边的「订单」「客户」是完全不同的两回事，同名只是巧合。

u_s_siteinfo本站档案（只有一行）

一个部署一个站，所以这张表 id 恒为 1。整站的装修内容都塞在一个 JSON 里。

contentjson v3 分语言结构（老数据 v1/v2 也认）：顶层是共享层（图片、电话、地图点位），i18n 下按语言覆盖，缺的项按项退回默认语言 consolesecret 此处存明文，与 ERP 侧的密文是同一个密钥的两种形态 langs 开放语言，第一个是默认语言 status 前台开关，与 ERP 侧 u_s_site.status 是两个独立决定 notifyemail 询盘通知收件人

u_s_pageview前台浏览明细

前台的每一次页面浏览一行，是流量统计的原始事实。只保留 90 天，到期由 PageViewCleaner 批量清掉；算 UV 只看 visitorid（SITE_VISITOR Cookie 里一个 16 字节随机串，与买家账号无关）。

visitorid / sessionid 算 UV 的唯一依据；清 Cookie 或换浏览器就算新访客，这是这种统计方式的固有误差 pagetype / goodscode / pagepath / lang 看了哪一类页面、哪个商品、哪个语种 referrer 比 PV 值钱：区分「搜索进来的」和「直接输网址的」 device / browser 由 UserAgentParser 从 useragent 解析落列，不采集新数据 isbot 判定为爬虫的行照样入库，只在统计时排除——删了就永远找不回来 clientip 已截断，不是完整 IP；country 现在恒 NULL，留列等接了 IP 归属库再回填
u_s_pv_daily前台浏览日聚合

上面那张明细表的日聚合，一次上报往这里写两行：一行 _all（当天全站合计），一行真实页面类型。永不删除，是 90 天之后唯一剩下的历史。

pagetype = _all ⚠ 它不是一种类型，是当天全站合计；查趋势只读它，查分布和排行必须排除它，否则总数正好翻倍 pv / pvhuman 含爬虫 / 排除爬虫。看报表要看 pvhuman，pv 只用来估爬虫占比 uv ⚠ 今天这一行恒为 0，次日 01:50 才由 PageViewMaintenance 回填；且 uv 不能相加（同一访客会同时出现在 home 行和 detail 行） statdate 「一天」按 Asia/Shanghai 切，不按 UTC
u_s_rate汇率表（只有一行）

前台币种切换用的汇率，id 恒为 1，整表只有一行。后端启动后 30 秒拉第一次，拉到之前前台只有本币、不显示切换器（降级成没有这个功能的样子，不报错）。换算只发生在展示层：结算页回到本币，u_s_order 落的一律是本币，否则汇率一变老订单就对不上账。

base_code ⚠ 是汇率源返回值的基准，跟着 API 走，不是站点本币（站点本币在 u_s_siteinfo.currency）；混淆会让换算方向整个反过来 ratesjson 自动拉回来的完整汇率表，相对 base_code overridejson 运营手工覆盖，逐币种压过 ratesjson；给汇率加 buffer 或 API 挂掉时兜底 fetchtime / fetchstatus / fetcherror 最后一次成功拉取的时间与结果，超 7 天管理台标红
u_s_schema_migration迁移台账

人工登记这个库跑过 sql/station/migration/ 下的哪几个脚本。不是 Flyway：没有校验和、不阻止乱序、不自动执行任何东西，准确性靠人——跑完忘了登记，台账就是错的，而错的台账比没有台账更危险。

source ⚠ 最关键的一列：执行=确实跑过；回填=无执行记录、只是按结构比对确认改动已生效。两者可信度不同，别混着看 filename 与 migration 目录下的文件名一字不差，用它做主键

07 / 陷阱看库时最容易想错的地方

下面每一条都是结构里真实存在的、但从表名和列名读不出来的东西。

01同名反向的两个 paidamount

采购单 u_p_purchase.paidamount 是「付出去的钱」；销售订单 u_o_order_*.paidamount 是「收进来的钱」。freightamount 同理：订单主表是向客户收的，发货批次是自己付的。

02consolesecret 两边不能对拷

ERP 的 u_s_site.consolesecret 存 AES-GCM 密文，站点的 u_s_siteinfo.consolesecret 存明文。同一个密钥的两种形态。直接从 ERP 库 SELECT 出来粘到站点库不会报错，只会每次跳转都验签失败，日志上看着像代码 bug。

03一个商品在一个仓里有四行

u_m_stock 主键含 qualityflag 和 onhandflag。统计「某商品总库存」时忘了聚合这两列，拿到的只是良品在库那一格。u_m_batchinfo 也一样。

04两个数量列不是一回事

physicalqty 是真有的货，lockedqty 是待审核出库单占的。可用量 = physicalqty − lockedqty，要自己减，表里没有这一列。reservedqty（原订单预占）已废弃、恒为 0，别再减它。

05月表落在哪个月，各单据不同

订单按 createtime，发货批次按 shipdate，采购到货按 senddate。一张订单的多个批次可能跨月——查批次不能按订单的月份去找表。

06u_f_docmain 的主键是复合的

是 (doccode, sourcedoctype)，不是单一 doccode。按单号更新时漏掉第二列会打到多行或打不中。

07已废弃但没删的列

orderdetail.reservedqty（恒 0）、orderdetail.stock_source 和 shipbatchdetail.stock_source（恒「现货」）、u_s_user.password（恒 NULL）、订单的 buyershop / buyeruser（恒空串）。留着只为不动历史行，读它们没有意义。

08两个 status 不是副本

ERP 的 u_s_site.status 管的是「还发不发跳转令牌」；站点的 u_s_siteinfo.status 管的是「前台开不开」。lastaccesstime 也只表示「有人点了进入管理」，不表示进成功了。

09goodsinfo 和 goodssummary

前者是人写的自由文本，后者是按明细整体重算的一句展示摘要（「可乐等3种」）。名字太像，只能靠这条记住：带 summary 的那个不参与任何计算。

10定制件的专属批次

u_m_batchinfo.owner_orderdetailcode 非空时，这批货只能发给那一条订单明细，出库挑批次时别人一律跳过。判定一律用这一列，owner_ordercode 只是展示用。

11大量冗余快照列是故意的

goodsname / spec / unit / warename / partnername 这些在明细表里到处重复，是建单当时的快照，不跟主数据联动。改了商品名，历史单据上仍应该显示旧名字。

12数行数别用 table_rows

information_schema.tables.table_rows 对 InnoDB 只是估算值，偏差可以很大。核对数据一律用 COUNT(*)。

命名约定速记。前缀 s_ = 系统/租户，u_m_ = 主数据（master），u_f_ = 流水与凭证（flow），u_p_ = 采购与生产（purchase / production），u_o_ = 订单（order），u_s_ = 站点（site）。带 _YYYYMM 后缀的一律是月表，由 MonthlyTableInitializer 自动创建。

单号前缀：RK 入库 · CK 出库 · DB 调拨 · SC 工单 · SCPF 配方 · YZ 预占（已废弃：预占机制已取消，生成器里只剩常量和一条单测，无任何生产调用，不会再有新单号） · KH 客户 · GC 商品分类 · DLZ 独立站 · 站点侧 XP 询盘 · DD 订单 · LT 会话。

依据仓库内 sql/01_schema_and_init.sql、sql/station/01_station_schema.sql、sql/migration/* 与 MonthlyTableInitializer.java 整理。月表列的是模板，实际表名带 _YYYYMM 后缀。
