## 一、两个系统的关系

```
    康晨的独立站（新系统）                     康晨的 ERP（现有系统）
  ┌────────────────────────┐              ┌─────────────────────────┐
  │ 面向海外买家：          │  订单 ──────▶│ 销售订单 → 采购 → 生产   │
  │   浏览 / 询盘 / 下单    │              │                         │
  │ 面向康晨员工：          │◀────── 进度  │ 工单状态 / 发货批次      │
  │   商品 / 报价 / 订单    │              │                         │
  └────────────────────────┘              └─────────────────────────┘
        独立库 · 独立服务器                        独立库 · 独立服务器
```

**独立站产生需求，ERP 消化需求。** 一条线，两个方向的数据。除此之外两边没有任何耦合。

一商家一套，1:1 配对：康晨的独立站对接康晨的 ERP。所以 ERP 侧不需要任何多租户改造，
ERP 地址和凭据就是站点的一项配置。

## 二、已定的决策

| # | 决策 | 结论 | 理由 |
|---|---|---|---|
| 1 | 部署形态 | **一站一部署，机器放在买家所在地区** | **买家在国外，站点放国内他们访问不了。** 地理决定「机器放哪」，商家决定「有几台」，见 §九bis |
| 1b | 全球覆盖 | **一个部署 + CDN 边缘缓存**，不按国家开机器 | 一个商家同时卖美国和欧洲是常态，而一个站只有一个库，拆不开 |
| 2 | 多租户维度 | **不做**。业务表不带 `site_id`，只有一张 `site_config` 单例表 | 物理隔离后该字段永远只有一个值，留着会误导后来的人 |
| 3 | 商家的站点数 | **国内站 + 国际站各一个部署**，各自独立库 | 两边的支付、合规、SEO、币种完全不同，见 §三bis |
| 3b | 国际站的语言 | **一个站多语言**，不是一语一站 | 线上现有的中文/英文/日语三条记录应合并成国际站的三种语言 |
| 4 | 商品源头 | **从 ERP 商品档案选品 → 复制快照到站点**，站点只维护展示层 | 一个商家两个站，手工录两遍会被骂；快照而非实时依赖，ERP 挂了不影响站点 |
| 4b | 订单来源标识 | **复用 ERP 现有的 `OrderPlatform` / `OrderPlatformStore`** | 独立站 = 一个平台，国内站/国际站 = 两个店铺。ERP 侧零改造，报表天然按渠道拆 |
| 5 | 库存展示 | **不展示库存，展示 MOQ / 阶梯价 / 交期** | 按单生产没有现货，同步过去的数字要么是 0 要么误导 |
| 6 | 连接方向 | **全部由站点发起，指向 ERP** | 客户机器在不同网络，ERP 不可能反向连进来 |
| 7 | 员工身份 | **来自 ERP**（一次性票 SSO 保留） | 康晨的员工档案统一在 ERP，站点不再单独建员工 |
| 8 | 员工权限 | **在站点，不在 ERP** | 站点的权限项（上架、装修、改价）ERP 的 `sys_menu` 里没有 |
| 9 | 买家进度 | **只显示状态节点，第一版不显示百分比** | `actualYQty/planYQty` 中途恒为 0，展示出来像「二十天没动」 |
| 10 | 技术栈 | **不再用 RuoYi 脚手架** | 它的价值在 CRUD + 菜单权限；这里的核心是状态机、支付、多语言 SEO |
| 11 | 订单权威 | **推送 ERP 成功那一刻权威转移**，之后站点订单转只读 | 推送前 ERP 不知道这张单存在，站点必然权威；之后两边都能改就是两份真相，见 §四bis |
| 12 | 退款 | **要做**，且默认路径是「只退款不退货」 | 跨境退货运费常高于货值，实务上多为补偿式退款 |
| 13 | 报关字段 | **不做**（HS 编码、原产地、申报货值） | 明确不纳入本期范围。记下来免得以后有人顺手加 |
| 14 | 时区 | **全库存 UTC**，展示按查看者时区 | 买家在国外、商家在国内。这条不定，后面所有时间显示都要返工 |
| 15 | 可替换的外部依赖 | **支付、对象存储、统计都做成 provider 接口** | 国内站微信/阿里云，国际站 Stripe/R2，一份代码要都支持，见 §三bis |
| 16 | 客户定制需求 | **三层机制：配置 > 扩展点 > 改主干必须回流** | 少量大客户是代码分叉风险最高的组合，见 §九 |

## 三、系统形态

> ⚠ **这一节描述的三件套目录从来没有建过。** 仓库里**没有任何 `station-shop` 目录**
> （这个文件是全仓库唯一提到这个名字的地方）。现役的三件是：
> `station-console`（后端，Spring Boot **4.0.6** + 普通 `mybatis-spring-boot-starter`，
> 包名仍是 `com.ruoyi.station.console`）、`station-site`（Nuxt 前台）、
> `station-console-ui`（Vue3 管理台）。技术栈与下面写的也不同：不是 Spring Boot 3 与
> MyBatis-Plus，也没有「不再用 RuoYi 脚手架」——权限串 `site:*`、前端的 `v-hasPermi`
> 都是从 ERP 那套沿用的。**2026-09-18 整理时加注。**

```
（以下为当年设想，未落地）
station-shop/
├── station-shop-server/     Spring Boot 3 + JDK 17 + MyBatis-Plus，一个后端三套 API
│   ├── /api/shop/**         匿名 + 买家
│   ├── /api/admin/**        康晨员工
│   └── /api/internal/**     预留
├── station-shop-web/        Nuxt SSR —— 买家侧（匿名和登录同一套）
└── station-shop-admin/      Vue3 SPA —— 员工侧
```

**一个后端就够，不拆微服务**——这个体量拆开只会把精力浪费在分布式事务上，而且没有任何
需要独立伸缩的部分。三套 API 用不同的鉴权拦截器分开即可。

**匿名和登录买家不拆**：它们共享商品页、路由、SEO 结构，拆开就是同一批页面写两遍
（这个仓库已经为此吃过一次亏，见盘点文档 §二.3）。

**员工端必须拆出去**：SEO 站要激进缓存、后台不能缓存，混在一个进程里迟早出事。

## 三bis、国内站与国际站

一个商家两个站、两台服务器、两个库。**它们的差别不是部署位置，是两套功能。**

| | 国内站 | 国际站 |
|---|---|---|
| 支付 | 微信 / 支付宝 | PayPal / Stripe / **电汇 + 水单** |
| 币种 | CNY | USD / EUR |
| 备案 | **必须 ICP + 公安备案，底部挂号** | 不需要 |
| 合规 | 个人信息保护法、电商法 | **GDPR / CCPA** |
| SEO | 百度 | Google |
| 统计 | 百度统计 | GA4 / Plausible |
| CDN | 国内 CDN（要备案） | Cloudflare |
| 单据 | 增值税发票 | 形式发票 Proforma Invoice |
| 物流 | 快递单号 | 海运/空运、报关、提单号 |
| 语言 | 中文一种 | 多语言 + hreflang |

### 一份代码怎么扛住这些差异

这是对「一份代码 N 份配置」纪律（§九）的**第一次真实考验**。支付、统计、物流是真的不同实现，
靠配置开关糊不过去：

- `site_config` 加 `site_mode`（`domestic` / `international`），决定装配哪套实现
- **支付做成 provider 接口**：`PaymentProvider` 下挂微信、支付宝、Stripe、PayPal、线下电汇几个
  实现，配置决定注册哪几个。**这个抽象必须一开始就有**，后加要把订单支付流程整个翻一遍
- 统计埋点、CDN purge 同理，做成可插拔
- **多语言逻辑国内站用不上，但代码不删**。国内站就是「只开了中文一种语言」的国际站——
  不要为它做减法分支，那是代码分叉的开始

### 对象存储也要抽 provider

国内站用阿里云 OSS / 腾讯云 COS，国际站建议 **Cloudflare R2**（出站流量免费，对图片站是
数量级差异；全球边缘覆盖也更好）。阿里云/腾讯云的海外地域**能用**，且海外地域绑自定义域名
**不需要备案**——新加坡/东京是它们的强项，欧美一般。

一个细节能让切换变简单：

- **腾讯云 COS、Cloudflare R2、MinIO 都兼容 S3 协议** → 主实现按 S3 API 写，这三个通用
- **阿里云 OSS 用它自己的 SDK**（S3 兼容接口不完整）→ 单独一个实现

两个字段决定要一开始就对：

- **`goods_media` 存 object key，不存完整 URL**。域名和 CDN 前缀由配置拼；
  存完整 URL 的话，换 CDN 域名要 update 全表
- **上传时生成多尺寸 + WebP**（列表小图 / 详情中图 / 原图归档）。商家传的是手机拍的 5MB 原图，
  一个商品页 20 张就是 100MB —— 这既是流量成本也是转化率问题，不是优化项

### 商品不要录两遍

两个库最难受的地方就是同一批商品要维护两次。解法是决策 4：

```
ERP 商品档案（已有）
      │  ① 上架时从中选品，复制一份快照到本地
      ▼
站点 goods：erp_goods_code + 展示层字段
      （多语言文案、图片、详情、挂牌价、阶梯价、MOQ、交期、上架状态）
```

- 基础档案（编码、名称、规格、单位）从 ERP 选，不手工录——「必须绑定 `erp_goods_code`」
  于是从一条约束变成自然结果，商家不可能忘记绑
- 展示层字段**两个站各自维护**，这本来就该不一样：国内写中文卖点，国际写英文 + 认证资质，
  价格更是两套
- **复制快照，不是实时依赖**，ERP 挂了不影响站点

代价是新增一个「ERP 商品档案只读接口」（站点出站调，方向与决策 6 一致）。这是唯一新增的
反向依赖，值得。

### ⚠ 域名不要用同一个靠 GeoDNS 分流

两个库、两套内容挂同一个域名按地区分流，Google 和百度会各自收录到错乱的内容，SEO 直接毁掉。
用两个域名或主域 + 子域（`kangchen.com` 国际 / `kangchen.cn` 国内），页脚放显式切换链接。

### 先做国际站

- 免备案，能立刻上线验证；国内站要等 2~3 周备案
- 多语言、SEO、询盘报价是它的主场，也是这个产品的核心价值
- **国内站 = 国际站 + 国内支付 + 只开一种语言 − GDPR，它是国际站的子集**，反过来不成立

先做国内站的话，多语言和询盘链路会因为「国内用不上」而被草草处理，做国际站时还得回头补。

## 四、两条成交路径，一套订单

外贸 B2B 的真实成交九成走询价，不走购物车。两条路径共用一套订单模型，入口和体验不同：

```
样品/小额  商品页 →「加入购物车」→ 结算 → 在线支付 → 订单
大宗      商品页 →「批量询价」→ 商家报价（锁价+有效期）→ 买家接受 → 订单 → 定金/尾款
```

因此：

- 商品详情页要有**两个按钮**，「批量询价」是主要转化点，不能藏在角落
- `order` 表要有 `order_type`（样品单 / 正式订单）和 `payment_terms`（全额 / 定金+尾款）
- 大宗订单的「支付」多半是**线下电汇 + 上传水单 + 人工确认**，`payment` 表不能只为支付网关设计
- 第一版要砍，砍在线支付网关，**不要砍询盘报价链路**

## 四bis、订单权威、改单与退款

### 权威在哪一边

一张订单在两个库里各有一份，必须有一条铁规则，否则两边各改各的：

```
下单 ─────── 支付 ─────── 推送 ERP 成功 ─────── 生产 ─────── 发货
└────── 站点权威 ──────┘ │ └────────── ERP 权威 ──────────┘
                    权威在此转移
```

- **推送前**：ERP 根本不知道这张单存在，站点必然权威
- **推送成功那一刻起**：ERP 权威，**站点订单转为只读**

界面上必须体现：商家在站点后台的改单按钮变灰，提示「已同步至 ERP，请在 ERP 修改」。
不这么做，规则就只是一句文档里的话。

### ERP 改了单，怎么回来

回流的不只是生产进度，还有**订单本身的变化**：被取消、被关闭、数量或金额被改、交期变了。
所以 §七 方向二的拉取接口不能只拉状态，要拉回订单的关键字段做比对。

买家订单页展示的是**拉回来的 ERP 当前值**（存在本地，不实时跨境调），同时保留一份**下单时
的原始快照**用于争议追溯。两个值都要留着。

### ⚠ 金额被改小，而买家已经付过钱

这是权威转移带来的必然冲突，**不能静默覆盖**——钱已经在你账上了，改个数字不会把钱退回去。

规则：ERP 侧的金额变化不直接改站点的已收金额，而是**产生一笔差额需求**：

- 改小 → 生成一条**待退款**记录，进退款流程
- 改大 → 生成一条**待补款**记录，通知买家补付

### 退款

**默认路径是「只退款不退货」。** 跨境退货的运费常常高于货值，实务上大多是补偿式退款或
部分退款，真要退货是例外不是常态。

状态机要留的边：

```
已支付 ──┬─▶ 退款申请中 ─▶ 退款处理中 ─┬─▶ 已退款（全额 / 部分）
         │                              └─▶ 退款拒绝 ─▶ 回到已支付
         └─▶（ERP 取消订单 / 金额改小，系统自动发起）
```

要点：

- **两种触发**：买家在订单页申请；ERP 侧取消或改小金额时系统自动发起
- **必须支持部分退款**（数量减少、质量补偿），不是只有全额
- **执行方式按支付渠道分**：Stripe / PayPal 走各自的 refund API；线下电汇只能人工退，
  系统里记录退款凭证和操作人
- **退款回调同样要幂等**，和支付回调一个道理
- **退款 ≠ 退货。** ERP 那边的 `SalesReship`（销售退货）是另一件事，不要把两者强绑——
  只退钱不退货是本系统的主路径，那种情况下 ERP 侧没有退货单
- 一张 `refund` 表：关联 order / payment、金额、原因、渠道、状态、操作人、凭证

> 状态机是最难事后改的东西——已有数据都要迁移。所以哪怕第一版退款全靠人工点，
> **这几条边也要先画在状态机里**。

## 五、数据模型骨架

```
site_config             单例。域名、语言列表、币种、装修 contentJson、ERP 凭据、SMTP、功能开关
site_user               买家账号（email 唯一）+ owner_admin_id
site_admin              员工影子账号（首次 SSO 进入时自动创建）+ 角色

goods                   商品 + erp_goods_code + moq / lead_time_days / sample_price
goods_lang              多语言文案（goods_id + lang）
goods_media             图片/视频（OSS key）
goods_price_tier        阶梯价（MOQ → 单价）
goods_owner             商品负责人（goods_id, admin_id）

cart / cart_item
inquiry                 询盘 + owner_admin_id
quotation               报价单（有效期 + 锁定单价）
`order` / order_item    订单（商品名/规格/单价全部冻结快照）+ owner_admin_id
order_status_log        状态流转记录（谁、何时、从什么到什么）
order_erp_status        从 ERP 拉回的进度（脱敏后的粗粒度状态）
payment                 支付流水（在线网关 + 线下水单两种形态）
refund                  退款单（关联 order/payment，支持部分退款，见 §四bis）
erp_outbox              待推 ERP 的事件 + 重试次数
admin_audit_log         员工操作日志：谁改了价、删了商品、导出了客户名单
```

### 几个必须一开始就定死的字段决定

- **金额用 `bigint` 存最小货币单位 + `currency` 字段**，不要 decimal 存元。多币种下单时把汇率冻进订单
- **订单号自己生成、带站点前缀、可读**（`KCCN-20260901-000123` / `KCIN-…`）。
  同一个商家的两个站是两个独立库、各自自增，**不加前缀推到同一个 ERP 必撞号**，而它是幂等键
- **订单行冻结快照**：商品名、规格、单价全部存一份。ERP 改了商品名，历史订单不能跟着变
- **状态机单向前进**，每次流转写 `order_status_log`。支付类系统查问题全靠它
- **`owner_admin_id` 字段先加上，逻辑可以后做**——后补要改全部查询，现在加是零成本

## 六、业务员负责制

外贸公司的客户资源是业务员的命根子，**「业务员只能看自己的客户」是刚需，不是可选项**。

| 角色 | 能看什么 |
|---|---|
| 管理员 | 全部 |
| **业务员** | **只有自己名下的客户、询盘、订单** |
| 运营 | 商品、装修、文件库；看不到客户和订单 |
| 财务 | 订单和收款；改不了商品 |

规则：

- **询盘自动分配**：商品页提交的询盘，直接分给该商品的负责人（`goods_owner`）。
  商品没设负责人就进公海，由管理员分。这是「按商品分工」唯一真正有价值的地方
- **客户跟着业务员走**：买家首次询盘/注册后归属某业务员，之后所有询盘订单都归他，不重新分
- **要有转移功能**：业务员离职，管理员批量转给别人
- **「一个业务员负责哪个站点」不需要建模**——一站一部署，他能不能进那台机器就是答案

### ⚠ 入口处不要做「选择业务员」的下拉框

如果进站前能随手选以谁的身份进入，业务员数据隔离就等于没有——选谁就能看谁的客户。

正确做法：**谁登录 ERP 就以谁的身份进站**。确实需要「代入别人看」的场景（经理查跟进情况），
做成一个只有管理员有的、**显式且留痕**的「以 XX 身份查看」功能。

### 身份与权限的分工

一次性票 SSO 保留，但兑换是**站点出站调 ERP**（方向与决策 6 一致）：

- ERP 只回答「这个人是康晨的张三，工号 xxx」
- 站点收到后自动建一条 `site_admin` 影子账号，**角色和权限在站点自己配**
- ERP 那边禁用/离职的人票据换不出来，自然进不来——这层联动就够了

## 七、与 ERP 的接口契约

> **⚠ 这一整节是二期及以后的目标态，一期一行都不做。**
> [boundary §8](./独立站与ERP的边界.md) 定的是「订单拉取 / 生产进度同步**一期不做，
> 也不预埋接口**」——不预埋是刻意的：预埋一个「暂时没人调」的同步接口，等于把互通提前建好了，
> 下一个赶进度的人会很自然地用上它，那时候「两边后端没有任何互通」这条就已经破了，
> 而且没有任何编译错误会提醒他。
>
> 一期的替代办法是**人工同步**：独立站出了单，人在 ERP 里录一张单。这不是将就——
> 手工这一步的存在，让「两边订单没有隶属关系」在流程上就是显式的。
>
> 后期真要做，协议要在那时候重新定（谁主动、频率、幂等键、失败怎么办、跨境网络抖动怎么办）。
> 下面这些是当时讨论的结论，作为那一天的起点保留，**不是现在的施工图**。

### 方向一：推订单（站点 → ERP）

支付成功那一刻**只做两件事**：改本地订单状态 + 往 `erp_outbox` 插一条。推送由后台任务做，
失败重试、超次数进死信、人工可重推。

> ⚠ ERP 挂了或者慢了，绝不能让买家的支付流程失败或超时。

幂等键是站点订单号，ERP 侧唯一索引，重推多少次只生成一张单。
`erp_goods_code` 为空的商品，订单标记为「待人工处理」而不是同步失败。

**订单来源用 ERP 现有的渠道模型，不新造字段**（决策 4b）：

```
OrderPlatform       platformCode = SITE      「独立站」
OrderPlatformStore  storeCode    = KC-CN     康晨国内站
                    storeCode    = KC-INTL   康晨国际站
```

推送时带上 `platCode` / `shopStoreCode`，`SalesOrder` 上已有这四个字段。
ERP 侧零改造，且销售报表天然能把独立站和其他渠道并列拆开。

### 方向二：拉进度（站点 → ERP）

站点定时轮询自己那几张单的状态，加随机抖动避免整点集中打 ERP。
B2B 订单完全不在乎几分钟的实时性。

## 八、生产进度映射（ERP 现状已核实）

> **⚠ 同 §七：二期及以后，一期不做。** 这一节的价值在于「ERP 那边的现状已经核实过」——
> 三条链的状态值、`sourceCode` 靠不住、备货型订单没有工单、订单和批次分月表，
> 这些事实到二期仍然成立，重新查一遍很费时间，所以留档。

ERP 现有三条链，状态都已实现：

| 链 | 状态值 | 位置 |
|---|---|---|
| 销售订单履约 | 草稿 / 待审核 / 已驳回 / 备货中 / 已备货 / 发货中 / 已完成 / 已取消 / 已关闭 | `SalesOrder` |
| 生产工单 | 待生产 / 待领料 / 生产中 / 已完工 / 已关闭 | `ProductionOrderServiceImpl` |
| 发货批次 | 待确认 / 已提交仓库 / 已打印单据 / 已发货 / 已完成 / 已取消 | `ShipBatch` |

**粒度到工单级，没有工序级。** `ProductionLog` 是领料/消耗/完工入库的单据日志，不是工序进度。

对外映射（**「买家看到」这一列是给前台的展示文案，不是 ERP 的内部状态名**）：

| 买家看到 | 来源 |
|---|---|
| 订单已确认 | SalesOrder 备货中 / 已备货 |
| 备料中 | ProductionOrder 待生产 / 待领料 |
| 生产中 | ProductionOrder 生产中 |
| 生产完成 | ProductionOrder 已完工 |
| 已发货 | ShipBatch **已发货** |
| 部分发货 | SalesOrderItem `shippedQty / qty` |

> ⚠ **别把左列当成 ERP 的状态值。** ERP 的销售订单状态只有
> 草稿 / 待审核 / 已驳回 / **已备货** / 备货中 / 发货中 / 已完成 / 已取消 / 已关闭——
> **没有「已确认」这一档**，那一档叫「已备货」（`SalesOrder.STATE_READY`）。

「已发货」用 `ShipBatch.STATUS_SHIPPED`，**不要用「已完成」**——这两个词在 8-28 的改造里
刚被拆开。按 `ShipBatch.java` 的注释，它们的区别是：

- `STATUS_SHIPPED`（已发货）= 货已装箱、承运商与物流单号已录，**但货还在仓库里、库存也一分没扣**；
- `STATUS_COMPLETED`（已完成）= 承运商已把货取走、销售出库单已过账、**库存已扣**，
  注释写「这一刻对应现实中货真的离开仓库」。

（所以「不要用已完成」的理由不是「财务口径会晚几天」，而是**已完成在业务上就等于货已离仓**；
这个位置原来写反了，2026-09-18 整理时按代码注释改正。）

### ⚠ 四个坑

1. **合并工单会串客户数据。** `ProductionOrder.orderAllocation` 允许一张工单的产出分配给
   多张销售订单——康晨可能把 A、B 两个客户的同款货合成一张工单。接口必须只取
   「分配给这个买家那张单的那一份」，**绝不能返回整张工单**。
   同理 `materialCost` / `processingCost` / `unitCost` 一个都不能出去。
2. **`SalesOrderItem.sourceCode` 靠不住。** 它只存当前挂的工单号，工单关闭时会被清空，
   代码注释自己写了「不能拿来做历史追溯」。算整单进度走 `selectOrderProductions`（按分配 JSON 反查）。
3. **备货型订单没有工单。** 普通件直接从库存发，压根不排产。映射要能处理「无工单」的情况，
   从「已备货」（前台展示成「订单已确认」）直接跳到「待发货」，不能卡在一个永远不动的「生产中」上。
4. **订单和批次分月表**（`u_o_order_{yyyyMM}`、`u_f_shipbatch_{yyyyMM}`）。
   买家查历史订单是跨月的，取数不是一句 select。

**脱敏映射写在站点这边**，别指望 ERP 输出时记得脱敏。

## 八bis、一站一服务器：为什么、放哪、多少钱

> 2026-09-06 从已删除的 `station-platform-architecture.md`（§2/§3/§4/§10）并过来的。
> 那一份的其余章节要么被 [独立站与ERP的边界.md](./独立站与ERP的边界.md) §12 整节作废，
> 要么在本份 §九 / §九bis / §十一 / §十三 里有更细的版本，所以整份删掉了。

§九 讲的是「N 台机器怎么管」，这一节先回答它的前提：**为什么非得一站一台、每台放哪、要花多少钱。**

### 为什么是一站一服务器

最初的评估是**反对**的，理由是「N 倍运维成本」。后来推翻了，四条理由：

1. **地理位置是真收益，而且换不来。** 印刷站客户在欧洲就放欧洲，食品站客户在美国就放美国。
   一台机器不可能同时离两个洲都近。这是「一站一台」**唯一无法用别的手段替代**的好处。
2. **故障隔离。** 一个站被攻击、被爬虫刷、进程崩了，不连累别的站。
3. **可整机交付。** 以后把某个站卖给客户，直接把那台机器给他，不用从共享环境里往外摘数据。
4. **服务器不贵。** 境外 2核4G 一台一年几百到两千元，10 个站一年不到两万。
   对比一次超卖事故或者一次数据泄露，这不算钱。

**原来那条反对理由为什么不成立**：当时算的是「一台机器上跑 10 个站的进程，内存装不下」。
在一站一台的前提下，每台机器只跑一个站，那笔账根本不存在。

真正的代价不是钱，是运维——那一条是真的，解法在 §九。

### 放哪：延迟的账要算两头

商家（国内）点一次保存，请求要跨洋跑一个来回；买家（国外）则相反。三个方案的取舍：

| 服务器放哪 | 国外买家 | 国内商家 | 线路稳定性 |
| --- | --- | --- | --- |
| **美国 / 欧洲（选定）** | 最好，20~50ms | 差，一次保存 1 秒起 | ⚠ 中美线路晚高峰丢包，**可能保存失败** |
| 香港 / 新加坡（未选） | 中等，150~250ms | 好，30~90ms | 稳定得多 |
| 国内（未选） | 差，200~400ms 且丢包 | 最好 | 稳，但要 ICP 备案 |

选第一行，是因为**买家体验和谷歌收录优先**，商家那边由内部人承担。备案那一项见 §九bis
（海外部署 + 海外域名，备案整件事不存在）。

具体每个站放哪个国家，按该站的**买家主要在哪个洲**选：美国/北美 → 美东（弗吉尼亚一带）；
欧洲 → 德国法兰克福；分散在多个洲 → 美东，它到欧洲和到亚太都不算太差。
全球覆盖靠 CDN 而不是按国家开机器，见 §九bis。

### ⚠ 因此必须做的一件事：写操作要有重试和明确的失败提示

「慢一点」和「有时候失败」是两回事。中美线路在晚高峰丢包严重时，管理台的写操作会超时。

**管理台的所有写操作必须有重试和明确的失败提示。** 不能让商家点了保存之后不知道成没成——
那会导致重复提交，或者以为保存了其实没有。这是选了「服务器放境外」带来的直接开发要求，
不是可选优化。

### 每台机器上装什么

```
一台独立站服务器
├── nginx              收请求、管证书、按路径分流（全是 127.0.0.1，没有跨机器路由）
├── 前台 Node 进程      Nuxt SSR，:3000，买家看的网站
├── 管理台 Java 进程    :8081，商家用的后台
├── 管理台前端 dist     后台的静态页面
├── MySQL              这个站自己的库（是正本，不是副本，见 boundary §5）
└── Redis              管理台会话
```

**配置**：内存 **至少 4G**（MySQL 1G+、Java 512M、Node 250M、Redis 和系统还要一些），
建议 2核4G 或 2核8G，硬盘 50G 起。

| | 一台一年 | 10 个站一年 |
| --- | --- | --- |
| 腾讯云/阿里云 境外轻量 2核4G | 约 500~1500 元 | 5000~15000 元 |
| Vultr / DigitalOcean 2核4G | 约 2000 元 | 约 20000 元 |

**为什么管理台也放这台**：全部在一台机器上，nginx 里全是 `127.0.0.1` 的转发，没有跨机器路由、
没有跨机器的证书和认证。代价是商家访问要跨洋，见上面那张延迟表。

具体怎么装见 [独立站部署手册（Windows）.md](./独立站部署手册（Windows）.md)（Windows）
和 [独立站部署手册（Linux）.md](./独立站部署手册（Linux）.md)（Linux）。

### 10 台机器的代价，摊开看

| 事情 | 1 台 | 10 台 |
| --- | --- | --- |
| 改个功能发版 | 传一次 | 10 次，**一次都不能漏**。漏一个，那个站行为不一样，而且它看起来是好的 |
| 证书 90 天到期 | 一年 4 次 | 一年 40 次，忘一次那个站直接打不开 |
| 数据库备份 | 一条命令 | 10 条，还要检查有没有真的跑成功 |
| 系统打补丁 | 一次 | 10 次 |
| 半夜某个站挂了 | 你知道 | **可能三天后才知道** |

**解法不是少开站，是从第一台开始就不手工操作**——具体四件事（迁移、证书、凭据、备份、
升级顺序）见 §九「会在 N 台机器上被放大的五件事」。

### 第一台机器要当模板做，不是当第一个站做

装第一台的时候，每一步写进脚本、每个配置参数化（站点名、域名、密钥都从配置读）。
装完之后，第二台应该是「跑一遍脚本改几个参数」，而不是「再手工装一遍」。

多花两三天，省下后面 9 次重复劳动，以及那些必然会犯的手工错误。

## 九、一客户一台机器：真正的成本在运维

### ⚠ 唯一会要命的事：代码分叉

这类项目十有八九死在「A 客户要个特殊功能，就在 A 那台机器上改了代码」。半年后八个客户
八个版本，谁也不敢升级谁。

**一份代码，N 份配置。** 客户差异只能是配置或数据，不能是代码分支。每台机器要能一眼看出
版本（`/api/version` 返回版本号 + 构建时间）。

### ⚠⚠ 只给大客户开站，让这条风险变成最高的一条

「只有大型客户才开独立站」这个定位是对的，但它把代码分叉的风险推到了顶点：

> **N 小 + 客户大 = 分叉风险的最高组合。**

小客户多的时候可以说「这是标准功能，不改」。大客户少的时候，每家占你 20% 的收入，
他提的需求你很难拒绝，而且他付得起钱让你改。

光靠自觉守不住，需要一个**能对客户说出口的三层机制**（决策 16）：

```
客户提定制需求
  ├─ 第一层：能用 site_config 的配置项满足吗？   → 直接做
  ├─ 第二层：能做成一个扩展点 / 插件吗？          → 做，但接口是通用的
  └─ 第三层：必须改主干                          → 改，但**必须回流成通用功能**，
                                                   其他客户默认关闭
```

第三层的关键是「回流」：改完之后主干仍然只有一份，别人只是没打开开关。
**绝不允许出现「这个功能只在康晨那台机器上有」。**

商务上配一句话：定制可以做，但产权归你们、会成为产品的一部分。大客户通常接受这个条件。

### 可用性：不能再说「接受单点」

大客户的官网是他公司的门面，挂一天会打电话，挂两次会影响续费，而且采购合同里多半有
SLA 条款。分三档，按客户要求上：

| 档 | 做法 | 何时上 |
|---|---|---|
| 最低 | 进程自动拉起 + 每日快照 + **恢复演练做过一次** | 第一个客户就要有 |
| 中 | 数据库主从（同区域第二台）+ 监控告警到人 | 第二个客户 |
| 高 | 双机 + 负载均衡 | 客户在合同里要求时 |

**「恢复演练做过一次」这条别跳。** 没验证过的备份等于没有，而发现它没用的那天，
正好是最需要它的那天。

### 大客户还会要这两样

- **经营看板**：这个月多少询盘、转化率、哪个业务员跟得好、哪个商品带来的询盘最多、
  流量来自哪些国家。数据都有（`inquiry` / `order` / `pageurl` / `owner_admin_id`），
  缺的只是一个聚合页面。大客户管理精细，这个一定会被问
- **操作审计**：他们的 IT 部门会走安全评审。谁改了价格、谁删了商品、谁导出了客户名单——
  `admin_audit_log` 这张表**字段要一开始就加**，事后补不出历史

### 开一个新站是十七步，要有清单

数一下：注册域名 → 实名 →（国内还要备案）→ 买服务器 → 装环境 → 建库 → 跑迁移 →
部署三个服务 → 申证书 → 配 DNS → 配 CDN → 建对象存储桶 + 子账号 → 配 SMTP + SPF/DKIM →
申支付账号 → 配 ERP 凭据 → 导入商品 → 建员工账号。

客户少的时候手工可以接受，**但那份清单必须有**——漏 SPF/DKIM 这类事和客户数量无关，
第一个客户就会踩，而且表现是「客户说没收到邮件」，你查日志却发现明明发出去了。

### 会在 N 台机器上被放大的五件事

| 事项 | 做法 |
|---|---|
| **数据库迁移** | 上 Flyway。手工跑 SQL 在 N 台机器上必然漂移，且没人知道哪台跑到哪版。迁移脚本**只加不删**，因为升级中会短暂出现「新库 + 旧代码」 |
| **证书续期** | acme 自动续。90 天有效期靠记日历，N=3 就会漏 |
| **OSS 凭据** | 一站一份子账号/STS，权限限死在自己的目录前缀。AK 落在 N 台客户机器上，一台泄露不能波及全部 |
| **备份** | 每台各自配（本地 + 异地），并且**真的恢复演练一次**。客户的订单数据只存在他那台机器上 |
| **升级顺序** | 自己留一个样板站先升，跑冒烟再推客户。Java 包能回滚，数据库迁移过了退不回去 |

监控最低限度：每台三个进程（Node / Java / MySQL）挂了要有人知道。不用上 Prometheus，
一个 curl 健康检查 + 挂了发邮件的脚本就够，但必须有。

### 品牌与发信域名

站点上不能出现你们的品牌。最容易漏的是**邮件**：询盘通知、订单确认如果从你们的域名发出，
一是康晨的客户收到陌生域名的「订单确认」专业度归零，二是**大概率进垃圾箱**（发件域名与
网站域名不一致，反垃圾判定为钓鱼）。

每个部署要配商家自己的发信域名，并让商家在自己的 DNS 上配 **SPF + DKIM**。
这条要进「新客户上线清单」，和域名、证书并列。

### 数据归属

数据在客户机器上，属于客户。留的运维账号要让客户知情并写进合同，别做成暗门。
按年收费的话需要 License 机制，建议**软到期**（前台照常运行，后台弹提醒并限制新增功能）——
硬性停机会让客户官网直接打不开，纠纷很难看。这条要和商务口对完再定。

## 九bis、跨境部署：站点在国外，ERP 在国内

这是「一站一部署」真正的理由：**买家在国外，站点放在国内他们访问不了。**

但要把两个维度分开：

```
放哪台机器   ← 由「这个商家的买家主要在哪」决定
有几台机器   ← 由「有几个商家」决定
```

### 全球覆盖靠 CDN，不是按国家开机器

一个商家同时卖美国和欧洲是常态，而它只有一个站、一个域名、一个库——**不可能在两地各部署
一份**，那是两个独立的库，同一个买家在两边看到的购物车都不一样。

正确做法：服务器按该商家的主要市场放一台，全球覆盖挂 CDN。这套系统的流量结构天然适合：

| 内容 | 占比 | 可缓存 |
|---|---|---|
| **商品图片** | 页面重量 80% 以上 | ✅ 缓存一年 |
| 商品列表/详情（SSR HTML） | 绝大多数请求 | ✅ 公开内容 |
| 买家登录后的页面 | 低频 | ❌ 量很小 |
| 询盘 / 下单 | 极低频 | ❌ 回源即可 |

装修页那句「保存后刷新立刻生效」用**主动清缓存**保证：保存装修或改商品时后端调一次
CDN purge API。比缩短 TTL 干净。

> 需要在某个国家单独开机器的理由不是速度，是**合规**（数据驻留），见下。

### 跨境带来的四个必改点

**1. ⚠ OSS 必须换成海外节点** —— 最容易漏，漏了等于白部署。
站点在美东、图片还在杭州，页面最重的那部分照样慢。换海外区域 Bucket（或 R2 / S3），
或至少给国内 OSS 开海外 CDN。**要在里程碑第 2 步之前定**，图片 URL 的生成规则跟着变。

**2. SSO 从「回调验票」改成「签名令牌」。**
现在是站点拿票回调 ERP 兑换——同机内网几毫秒，跨境是 200~400ms 同步往返，而票只有 60 秒
有效期，网络一抖就换不出来，表现是「点进后台白屏」且极难查。
改成 ERP 签发带签名的令牌、站点**本地验签**，零跨境调用。
附带好处：ERP 临时不可用时员工照样能进后台。

**3. 站点→ERP 的调用全部异步，一个同步依赖都不留。**
超时放宽到 30 秒以上、指数退避重试；进度轮询拉长到 15~30 分钟一次。
**任何买家能触发的请求都不许同步等 ERP** —— 这条当硬约束写进代码规范。

**4. 员工后台会变慢**（买家在国外，业务员在国内）。
建议**接受它，不要为此拆库**：后台是低频交互，慢 200ms 感知不强；拆成两地或让后台跨境连库
是灾难级复杂度。难受就给后台域名也挂 CDN 或走加速线路，那是运维层面的事。

### 意外收获：不用 ICP 备案

站点部署海外 + 海外域名，**备案整件事不存在**，原计划里 2~3 周的硬等待消失。两个前提：
域名不能解析到国内服务器、不能用国内 CDN 节点；ERP 那台国内服务器如果有对外域名，它那份
备案照旧。

### ⚠ 新增风险：GDPR

服务欧盟买家就落进 GDPR——存的是欧盟自然人的姓名、邮箱、公司、询盘内容，全是个人数据。
第一个欧洲客户上线前必须有：

1. Cookie 同意横幅（非必要 Cookie 含 GA，需先同意）
2. 隐私政策页（收集什么、存多久、给谁）
3. **账号删除 / 数据导出** —— 买家的法定权利，不是产品功能
4. 欧盟买家数据尽量存欧盟境内 —— 这才是「按地区部署」真正硬的理由

加州 CCPA 类似但更宽松，按 GDPR 做即可覆盖。统计工具优先 Plausible 这类欧盟托管的，
GA 往美国传数据在欧盟有争议。

## 十、老仓库：捞什么，扔什么

> 实际落地走的是**在原地改造**：`station-console` / `station-console-ui` / `station-site`

> - `station-console` **没有扔**，它是现役站点后端，扔了线上就没了；
> - `/openapi/site/**` **没有扔**，前台现在就是靠它取数的；
> - `station-console-ui` **不是「起点」**，它本身就是现役员工端。
>
> 下面「捞走」里的技术判断（SSR、多语路由、hreflang、富文本白名单、询盘通知的做法）仍然有效，
> 只是它们本来就在原仓库里，不是「捞」过来的。**2026-09-18 整理时加注。**

### 扔掉（当年设想，未采纳——见上）

- ~~`station-console` 整个服务 —— 它的全部设计理由是「管理台不许有库」，这个前提没了~~
- ~~`/openapi/site/**` 和 `/openapi/console/**` 两套接口~~
- ERP 里 `sdsstation` 六张表和 7 个 Controller：**这半句现状是对的**（ERP 侧确实已经没有这些表和
  Controller 了，2026-09-03 拆库完成）。但后半句「新库重新设计，不要拿老表改」**与事实相反**——
  站点库就是**沿用 `u_s_*` 表名原样搬过去**的（boundary §5.3、`sql/station/01_station_schema.sql`）

### 捞走（这些是真金）

- **`station-site` 整个前台**：SSR 的选择、`/ja/products` 路径前缀多语、`pages:extend` 那层
  运行时语言路由、hreflang / canonical / sitemap。这些结论在新系统里一模一样成立
- **`contentJson` 的结构**（共享层 + `i18n.<lang>`，取不到回退默认语言）。
  ⚠ 编号已变：**现在是 v3**（服务端向前兼容 v1/v2/v3/v4，见 `sql/station/01_station_schema.sql:91`、
  `SiteOpenService.java` 的兼容分支）；本份写「v2」是当时的值
- `station-console-ui` 的页面（商品、文件库、装修、询盘）作为员工端起点
- **富文本白名单过滤**（`RichTextCleaner`）—— 商家能自由录入详情，这条必须在服务层做
- 询盘通知「先落库再发信、发信异步、失败全吞」的做法
- 一次性票 SSO 的票据协议（`SecureRandom` + 原子兑换 + 60 秒有效期）

## 十一、里程碑

顺序的依据是「尽早到达第一个活着的形态」。

| # | 内容 | 说明 |
|---|---|---|
| 1 | 库表 + SSO 接入 + 员工影子账号 + 商品 CRUD（多语言、OSS） | |
| 2 | **前台迁移：商品列表/详情/装修/多语言路由** | 跑通「员工上架 → 前台看得见」一整圈。**在此之前所有代码都没被验证过** |
| 3 | 买家账号 + 购物车 + 下单 | 支付先用「模拟已付款」按钮 |
| 4 | 订单推 ERP（outbox + 重试 + 幂等） | **二期**。一期人工在 ERP 录单，且不预埋接口（boundary §8） |
| 5 | **进度回流 + 改单回流 + 买家订单详情页** | 这是整套系统最有价值的功能，见下。回流部分同样是**二期** |
| 6 | 询盘 → 报价 → 转订单 | |
| 7 | 接真支付网关 + **退款流程** | 唯一没法反复重跑的环节，等骨架稳了再接 |
| 8 | 业务员数据隔离逻辑 | 字段第 1 步就加，逻辑可以放到这里 |
| 9 | 经营看板 | 大客户必问，数据都已经有了，缺的是聚合页面 |

> 退款的**状态机边**在第 3 步就要画进去，不能等到第 7 步——状态机是最难事后改的东西，
> 已有订单都要迁移。第一版哪怕全靠人工点按钮，边也要先在那儿。

### 为什么第 5 步是核心

外贸买家最大的焦虑是「我的货到底做了没有」，现在全靠邮件催业务员。让买家自己登录就能看到
订单在哪一步——**这个数据 ERP 本来就有，只是从没露给客户看过**。

**这是把独立站和 ERP 放在一起做的唯一充分理由。** 没有这条，独立站用 Shopify 就够了。

## 十二、容易漏、漏了要返工的实现细节

不影响架构，但都是「上线后才发现、改起来很贵」的：

| 事项 | 说明 |
|---|---|
| **多语言的真实负担是翻译** | 100 商品 × 3 语言 = 300 段文案。现实是功能做好了、商家只填中文，多语言白做。接一个机器翻译（DeepL / Google Translate API）出初稿让商家改，两天工作量，但决定这个功能能不能真用起来 |
| **询盘表单是垃圾信息磁铁** | 一天几十条垃圾是常态，还会污染业务员的分配队列。honeypot 隐藏字段 + 按 IP 频率限制 + 可选 Cloudflare Turnstile，半天工作量 |
| 商品搜索 | MySQL `LIKE` 在中文下基本不能用。第一版用**全文索引**（中文 ngram 解析器）+ 分类属性筛选。真不够再上 Meilisearch，别为此在每台机器上加一个 ES |
| 样品单可能卖出没货的东西 | 样品单是即时付款的，付完才发现要等 25 天体验很差。给商品加「样品现货」标记，或在下单页明写「预计 X 天内发出」 |
| 汇率 | 报价锁价到付尾款可能隔几个月。汇率差谁承担是合同条款，但字段要预留（订单锁汇率 / 尾款按当时汇率） |
| 本地测不了支付回调 | Stripe / PayPal 要回调公网地址。接支付之前先准备好 staging 或 ngrok 类工具，否则会卡住 |
| CDN 前置时的回调路径 | 支付回调不能被缓存或拦截，要显式配 bypass |

## 十三、还没定的

| 事项 | 说明 |
|---|---|
| **做产品还是解决一家** | 若只服务康晨一家，Shopify + 一个订单同步服务两周能上线，成本低一个数量级。本文全部按「要做产品」写 |
| 收单渠道 | 海外买家基本是 PayPal / Stripe。Stripe 优先用 Checkout / Payment Link，别自己收卡号（PCI 合规成本） |
| 收款主体 | 中国公司收美元，Stripe 需要港/新实体，或 PayPal 商业账户 + 跨境收款通道。商业问题，但决定接哪个网关 |
| **对象存储选型** | 国际站 R2 还是阿里云海外地域。**要在里程碑第 2 步之前定**，图片 URL 生成规则跟着变 |
| CDN 选型 | Cloudflare 是默认答案。要确认对目标市场的节点覆盖 |
| 国内站域名 | `kangchen.cn` 还是 `cn.kangchen.com`。不急，但备案要填域名 |
| License / 按年收费机制 | 见 §九，要和商务口对。建议软到期，硬停机会让客户官网直接打不开 |
| **个人数据出境的合法性基础** | 订单推给国内 ERP = 欧盟买家个人数据传中国，GDPR 下需要 SCC 等基础。**要问真正做跨境的法务**，技术上先做字段最小化 + 海外备份存海外 |
| 客户要求部署在他自己的云账号 | 大客户尤其国企背景会提。答应的话运维方式全变（没有 root、升级走对方变更流程）。建议默认不答应，要就单独报价 |
| 现有三条站点记录的合并方案 | 中文/英文/日语三条应合并成国际站的三种语言，装修内容按语言归位 |
