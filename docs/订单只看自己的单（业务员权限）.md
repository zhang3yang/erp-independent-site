# 订单模块横向权限 —— 业务员只看自己的单

> **它回答一个问题**：怎么让业务员在订单管理下的四个页面只看得到归属于自己的单。
> **它不回答**：菜单能不能进（那是纵向权限，RuoYi 原生的角色菜单授权），也不管财务模块。

**状态**：已实现（2026-09-11）。迁移脚本两个：
`20260911_sales_order_own_scope.sql`（销售订单）+ `20260911_order_own_scope_rest.sql`（其余三个）。

| 页面 | 权限点 | 归属字段 |
|---|---|---|
| 销售订单 | `order:sales:all` | `u_o_order.staffcode`（建单时的登录账号） |
| 发货批次 | `order:shipbatch:all`（或 `order:shipbatch:warehouse`，见 5.1） | `u_f_shipbatch.createuser` |
| 销售退货 | `order:salesreturn:all` | `u_f_docmain.createuser` |
| 销售补发 | `order:salesreship:all` | `u_o_sales_reship.createuser` |

判权规则四处共用一份：`com.ruoyi.system.utils.OwnershipScope`。

---

## 1. 为什么做

业务员在销售订单页看得到全店所有人的单，三个问题：

- **难找**：自己的单混在全店的单里，翻半天；
- **易错**：挨着的一行就是别人的单，点错了就是麻烦事；
- **没隐私**：同事之间的业绩互相看得一清二楚。

超管和商家管理员要看得到全部 —— 他们不做业务，只观察和管理维护。

---

## 2. 权限点

```
order:sales:all   查看全部订单
```

挂在「销售订单」(`fn8001`) 下面，`fn8042`，按钮级（`menu_type='F'`），
在角色管理的菜单树里勾选。

**语义是「能力」不是「限制」**：

| | 看得到 |
|---|---|
| 勾上 | 全店所有人的销售订单 |
| 不勾 | 只有归属于自己的 |

为什么不做成「只看自己」那种限制型权限 —— 配错方向的后果不对称：

- 能力型配错 → 业务员「怎么少了一半单子」，一眼看得出来；
- 限制型配错 → 限制压根没生效，**谁都不会发现**。

平台超管在代码里直接豁免，不靠这个权限点。

---

## 3. 归属认哪个字段

`u_o_order.staffcode` —— 建单时固定取登录账号，**不接受前端传值**，
之后任何改单都动不了它（`SalesOrderStaffAttributionSqlTest` 钉着这两条）。
它以后还要拿来算提成，是笔钱，所以本来就是可靠的归属依据。

**不是** `u_m_buyer` 上那个「归属业务员」—— 那个跟着客户走、会随客户转手变。

---

## 4. 拦在哪里

拦在 Service，不在 Controller 也不在前端。

### 4.1 列表

改的是 `resolveStaffNameFilter`。它本来就是 `staffCodes` 的**唯一出处**
（注释写着「一律由这里说了算」），也已经处理了空集合落成 `1 = 0`。
无权时把 `staffCodes` 与当前登录账号取交集。

**是交集，不是覆盖**：业务员搜同事的名字，正确结果是「一条都搜不到」。
覆盖成自己的单，会让他以为同事名下挂着这些单，比搜不到更误导。

「业务员账号」那个精确条件不用另外管：mapper 里它是 `and staffcode = ?`，
与 `and staffcode in (?)` 是 AND 关系，填别人的账号自然查不出东西。

### 4.2 详情与本人动作

七处，都在装载之后立刻 `requireOwnOrder(order)`：

```
selectOrderDetail  updateDraft  submitOrder  withdrawOrder
closeOrder  cancelOrder  deleteDraft
```

只拦列表不拦详情等于没拦 —— 前端「详情」按钮打的就是 `selectOrderDetail`。

### 4.3 另外三个模块

同一套做法，各自的落点：

| 模块 | 列表 | 详情与本人动作 |
|---|---|---|
| 发货批次 | `selectBatchList` 设 `ownerScope` | 详情、跨月查找、改批次、提交仓库、取消 |
| 销售退货 | `selectReturnList` / `selectPendingReturns` 设 `ownerScope` | 详情、删除 |
| 销售补发 | `selectList` 设 `ownerScope` | 详情、删除 |

`ownerScope` 是服务层专用的查询载体（`@JsonIgnore`，不是数据库列），
照 `SalesOrder.staffCodes` 的先例——**前端塞得进来，所以服务层每次都覆盖**。

两个「挑单」下拉也按<b>订单</b>的归属筛，否则业务员在这里就能把同事的订单挑出来：

- `selectShippableOrders`（新建发货批次的可发货订单）
- `selectEligibleOrders`（新建补发的可补发原订单）

⚠ 但 `receivable` / `refundable`（财务认领与退款）、`production-candidates`（生产排产）
**不筛**：那是财务和生产的工作台，按业务员归属筛等于让他们看不见活儿。

#### 退货单是共享的 DocumentMain

退货单用的是 `u_f_docmain`，入库、出库、调拨、生产走的是**同一条 mapper 语句**。
`ownerScope` 只在销售退货那两条服务方法里赋值，库存那几个页面从不设它，所以不受影响。
**别在共享路径上设这个字段。**

---

## 5. ⚠ 不该挡的路：挡了就把发货和回款搞停

这是本次改动**唯一真正危险的地方**。销售订单会被好几个别的模块按单号取走：

| 谁 | 走哪条路 | 为什么不能挡 |
|---|---|---|
| 仓库发货 | `findOrderAcrossMonths` | 仓库手里没有也不该有 `order:sales:all` |
| 财务回款 | `findOrderAcrossMonths` / `applyPayment` | 同上 |
| 生产完工回填 | `fulfillFromProduction` | 同上 |
| 销售退货 / 补发 | `findOrderAcrossMonths` | 同上 |
| 发货进度刷新 | `refreshShipProgress` | 由仓库发货触发 |

**这些路径一律不认归属。** 审核类动作（`confirmOrder` / `rejectOrder` /
`unconfirmOrder`）同样不挡 —— 审核本来就不是下单人自己做的。

`SalesOrderOwnScopeTest.跨模块按单号取单不认归属` 专门钉住这一条。

另外三个模块同理，各自放行的是：

| 模块 | 不认归属的动作 | 为什么 |
|---|---|---|
| 发货批次 | 打单 / 发货 / 驳回 / 完成 | 仓库处理的本来就是别人建的批次 |
| 销售退货 | 提交（审核即过账） | 动作本身不认归属；但⚠ **要先看得见才点得到**，见下 |
| 销售补发 | 发货 | 同上 |

`OrderModulesOwnScopeTest` 里的`仓库打单不认归属`、`入库员提交审核不认归属`钉住它们。

### 5.1 仓库发货页有自己的权限串，持有即代表看全部

```
fn5103  库存管理 → 仓库发货管理   order:shipbatch:warehouse   ← 持有它 = 看得到全部批次
fn8010  订单管理 → 发货批次       order:shipbatch:list
fn8043  └─ 查看全部发货批次       order:shipbatch:all         ← 只管上面那个页面
```

**「能进仓库发货页」和「只看得到自己建的批次」本来就分不开**：那个页面的全部工作内容
就是处理别人建的批次，库管员自己不建批次，只看自己的等于工作台永远是空的。
既然分不开，就别让它可配 —— 由权限串本身表达。

所以配一个库管员角色，**只勾库存管理这一棵树就够了，订单管理一项都不用给**。

> **这是改出来的，不是一开始就这样。** 最初两个页面共用 `order:shipbatch:list`，
> 系统分不出「这人是仓库还是销售」，横向权限只好另开 `order:shipbatch:all` 这个开关，
> 而它挂在订单管理树下。结果为了让库管员看全部批次，得给他一个订单管理菜单 ——
> 角色表单的「父子联动」默认开着，勾那一项会连带勾上父节点，库管员侧边栏就多出
> 一个用不上的「订单管理」，**看着像权限越界**。拆出独立权限串之后这个别扭就没了。
> 见 `sql/migration/20260911_shipbatch_warehouse_permi.sql`。

销售补发那边还是老样子：仓库要在补发页点「发货」，得有 `order:salesreship:all`
（补发只有一个页面，不存在两个页面共用的问题）。

### 5.2 销售退货：能不能提交，取决于看不看得见

「提交退货」按钮在**销售退货页的记录行上**。库存的「入库信息」页只查 `RK`（采购入库），
退货单 `XSTHRK` 不在那儿，所以没有第二条路。

提交动作本身不认归属，但**列表认**——看不见那一行就点不到按钮。
所以如果退货不是由建单人自己提交的，提交的那个角色也得勾上 `order:salesreturn:all`。

## 6. 没有登录上下文时放行

定时任务、内部调用、单元测试跑在没有登录上下文的路径上，一律放行，不筛成空。

理由：这七个方法都挂在 `@PreAuthorize("@ss.hasBusinessShop() and ...")` 后面，
而 `hasBusinessShop()` 自己就会取登录人、取不到直接抛 ——
**真实请求根本走不到没有登录上下文的那一步**。剩下会走到的只有测试和内部调用，
把它们挡成「一条都看不到」是拿业务中断换一个不存在的安全。

但**取不到登录账号时拒绝**（`requireOwnOrder` 里的 `me == null`）：
判权代码的失败方式必须是「拒绝」，不能是 500，更不能是放行。

## 7. 上线策略

**脚本跑完的那一刻，行为必须和以前一模一样。**

1. **迁移脚本**：建权限点，然后**发给现有的全部角色、全部商家**。跑完谁也没受影响。
2. **收权**：商家管理员到「系统管理 → 角色管理」，给业务员那类角色
   **取消勾选**「查看全部订单」。想什么时候收就什么时候收，可以一个角色一个角色地来。

新建的商家管理员内置角色会自动带上（`insertDefaultAdminRoleMenus` 发全部业务权限）。

回滚不需要回退代码：把权限重新发给所有角色即可。

## 8. 前端

`views/order/sales/index.vue` 只做一件事：无权时把「业务员账号」「业务员名称」
两个搜索框收起来 —— 只能看自己的单时，这两个框填什么都只会搜出空，留着纯属误导。

「业务员」那一列保留，让归属看得见。

真正的过滤在服务端，前端改不改都一样。

## 9. 已知边界

1. **四个页面按各自的 createuser 判归属**，不是按「订单的业务员」往下传。
   所以别人替你建的批次你看不到（他建的算他的）。目前没有「代建」场景，
   真出现了要么给他 `all`，要么改成按订单归属反查——那要跨月表拿订单号集合，代价大得多。
2. **销售补发的菜单归属待定（2026-09-11 挂起）**。补发功能还没投入使用。
   等用起来了要重新看一次：补发涉及发货，而发货物理上都在仓库，所以整单发货一定是
   库管员干的；但「决定补发并建单」是销售发起还是库管员自己发起，没定。

   - 只有库管员用 → 把「销售补发」菜单从订单管理挪到库存管理下（和「仓库发货管理」并排），
     库管员侧边栏就不会为它多出一个订单管理。菜单路径没有硬编码引用，挪动只改 URL，
     页面文件不用动。
   - 销售也要用 → 菜单留在订单管理下，库管员那边接受多一个订单管理入口。

   在那之前，库管员角色不要配补发权限——为一个没用起来的功能让侧边栏多一棵树，
   看着像权限越界。

3. **财务模块不做**。资金流水是财务的工作台，按业务员筛等于让财务看不见活儿。
   订单详情里的「收款流水」页签跟着订单走，订单看不到就进不去。
4. **订单列表的月份是分表的**，横向权限跟着每张月表走，不影响跨月查询。
5. **`order:sales:all` 是店内范围**，不跨商家 —— 列表本来就先按 `shop_code` 筛。
